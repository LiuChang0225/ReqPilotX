## 3. Excel 出错能证明什么

核对链路为：**原件 → 捕获 → Document Map → SourceItem/关联 → 拆分与分析 → 同版本 Matrix snapshot → UI/Excel**。

| 故障位置 | 如何判断 | 处理层 |
|---|---|---|
| 基线里表头已是 REQ，BOM 父级已错 | snapshot 和 Excel 忠实输出同一错误 | 上游业务映射/判定 |
| 基线或 snapshot 正确，Excel 漏派生、类型不同、顺序不同 | 同身份同版本逐项比较 | Matrix 投影或 Excel 写出 |
| UI 和 Excel 使用不同基线、意见版本或过滤范围 | 先比较版本、导出范围、对象集合 | 应用状态/版本读取 |
| 有图片绑定，但解码/透明遮罩失败 | 来源关系正确，渲染失败 | 资产兼容与导出器 |
| 内容存在，显示截断或行高不够 | 单元格实际值和图像仍完整 | 布局 |

既有空模板表导出 500 属于应用读取组装遗漏：Map 中的表未进入 export context，并非一定是 Map 错；已有修复。**正常导出由内部程序执行，不调用模型重读全文或重新理解 Excel。** 程序一致性通过也不等于源语义正确。

## 4. 原生应用优先的建议

当前已存在 App Server 自主任务、动态工具、反馈、中断/恢复及实际保存结果；不是尚未开始迁移。主要缺口变成了应用是否可靠地交付用户可见的业务阶段。

建议下一轮先完善 **Agent 原生应用 + 共用业务核心**，随后同步插件。这样能在一个入口固定来源角色、知识库选择、阶段发布、版本、人工反馈、恢复与导出，直接解决本轮暴露的体验问题。成本是独立插件的新手体验会稍后完善；保留 r13 可用性，不另建一套实现。

| 应用与程序负责 | Agent 保持自由 |
|---|---|
| 明确任务/来源/内部依据、阶段结果合同、保存与发布、进度事件、版本冲突处理、恢复和程序导出 | 决定先读哪里、何时重读、选择文本/表格/页图/OCR、追查引用、判定归属与粒度、修正候选 |
| 用户要求先看结构时，发布结构并在该确认点等待；已有有效确认按范围继承 | 在已授权阶段内自行调查，不为每张图、每个编号、每个拆分重复询问 |
| 无 KB 的分析分支跳过；明确显示当前产物、覆盖、不确定项与下一步 | 可以继续识别源内矛盾、缺少附件和待澄清内容，不输出无证据的符合结论 |

“硬工作流”应固定业务边界与交付责任，不固定所有阅读步骤。插件自然语言说明仍然必要，但关键阶段不能只依赖模型记住；共享核心提供可校验的阶段工件和状态，应用负责用户交互，插件提供宿主适配。不能复制两套状态机后靠提示词保持一致。

## 5. 执行顺序与交付界限

以下方案已获用户授权并开始实施；首轮完成情况见[实施与验证](2026-09-09首轮实施与验证.md)，详细验收见[测试计划](测试与评测计划.md)。

1. **P0：恢复顺畅核对与一致导出。** Q01/Q02/Q12：详情读取改造、同版共同类型投影、程序导出。先产出同文档性能对照及表内图片/独立图/扫描表的 UI–Excel 对照。
2. **P1a：任务入口和阶段成果。** Q03/Q04：启动即识别工作区和内部依据，尽早打开工作台；先结构，再条目及分类，后拆分处置与可选分析。长任务中断后仍能打开最近已发布成果。
3. **P1b：边界、关联和编号。** Q05–Q11/Q15：先识别封面目录整体，再恢复原编号叶级范围、完整表格业务单元、续表与共享上下文；同一来源顺序驱动首次发号/显示/导出。不要在错误结构上先做表面重编号。
4. **P2：PDF 策略及示例包。** Q13/Q14：复用已有算法捕获和关系候选；把本文难例整理为可执行示例与回归。首版核心示例伴随 P1 编写，不等全部案例齐全才动工。
5. **P3：插件等价入口。** 原生纵向流程跑通后，同步技能、脚本入口、示例和界面引导；从干净目录完成一次新文档分阶段运行和局部修订，证明共用核心没有依赖开发仓库隐式上下文。

不等待六案例全量语义完美或所有宿主实测才交付下一可用版；也不以某个样本能导出 Excel 宣称全部完成。Office继续暂停，历史编号与旧冻结包保留；本轮发布新的r14能力包，未重跑旧客户Matrix。
