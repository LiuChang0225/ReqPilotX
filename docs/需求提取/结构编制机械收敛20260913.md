# 结构编制机械收敛与 Luna Map 对照

更新：2026-09-13。本轮仅收敛从原件阅读到保存 Document Map 的机械编制，以及条目提交失败后的定位。原文理解、表格归属和拆分判断仍由 Agent 负责；不改前端，不增加第二套 Map 模型。

## 已查明的问题

对旧 Luna 06616 的公开工具调用去重审计发现：167 次调用中有 51 次 `task_describe`、88 次 `source_read`。说明入口增加并未消除编制负担，但不能把所有重读都算浪费：27 次同 scope 重读中，6 次在首次 Items 前，8 次用于修复，13 次用于原编号核查。

旧 Map binder 已经能编译来源标题，不能说 Agent 要手填所有标题。真正仍由模型承担的机械字段包括 node ID、parent ID、原编号重复填写、逻辑表 scope ID 和 owner ID。首次 Map 请求只有一个显式 title，却有大量身份和父级字段。

首次 `SOURCE_ITEM_STRUCTURE_ONLY_SPAN_NOT_TITLE` 失败实际指向 2.6 下的图注，并非封面。下一次才是封面/目录被编成 3 条非需求 SRC。旧错误没有指出 scope 和具体内容，迫使模型扩大回查范围。修复应定位到最早缺信息的接口，不能只增加抽象自查要求。

## 工具和 skill 变化

`map_apply.decisions.outline` 接受嵌套结构：Agent 只写实际角色、原件短引用、直属内容、子节点及所属逻辑表。程序生成稳定身份、父子/表所属引用，复用原有编号语法复制明确的原编号，再交给既有 `bind_map_edit` 和 Map compiler。父级移动、前面插入兄弟节点不改变已有身份；原文位置变化另论。

- `HEADING` 是原文标题，`CLAUSE` 是保留全文的编号正文；无标题段落放在真实父级 content。
- 封面、目录、文控没有独立标题时可按整组内容保存，不伪造来源标题。
- 表格继续由 Agent 明确片段、跨页续接和所属；辅助 evidence_refs 不冒充内容所有权。
- 原有细粒度 nodes/logical_tables 输入仍可用；单次不混用。省略旧节点不等于删除，修订和删除沿用既有明确操作。
- 来源覆盖、冲突、原序、坐标、保存、重放及工作台同步仍走原有实现；不会把未选内容自动当噪声排除。
- 条目语义验证错误增加 scope、Map 版本及可执行的 `source_read` 请求；图注误判类错误另带具体 content_ref 和文本片段，失败不会推进成果版本。

主 skill 加入默认入口和短 reference `compact-map.md`；字段按当前动作查询，仍保留逐页 MD、高清图、原件回查和工作台入口。旧任务若固定包不支持 outline，会明确拒绝新字段，不静默升级运行时。

## 确定性验证

同一份五页原件及旧 Agent 的完整语义选择，用传统请求和 outline 分别编译。按相同来源与定位建立严格身份对应后，完整 Map、逻辑表、全部单元格/合并信息、scope 内容及来源处置等价；仅有 2 个自动 evidence anchor ID 在证明来源/坐标完全相同后归一。旧运行 440 个文件未改。

| 指标（仅 Map decisions，不含传输外壳） | 传统输入 | outline |
|---|---:|---:|
| 紧凑 JSON 字符数 | 6,025 | 4,324 |
| 手填身份、父级、编号字段 | 70 | 0 |

文字量减少 28.23% 是本请求的表达成本差异，不是模型耗时降幅，也不证明旧语义错误自动修好。

最终 plugin 回归运行 197 项，通过，常规环境跳过 3 项 SDK 测试；另在实际 MCP SDK 环境执行这 3 项并全部通过，含真实 stdio 的 outline 提交。13 项 compact 专项包含在 197 项中，不相加。实际任务链覆盖保存、重放、稳定身份及错误回查指令。

## 冷启动对照范围

同一五页合成 PDF、相同 Map-only 业务请求、Luna max、无开发会话/旧答案、无子 Agent；两格分别固定 075307 和 095127。目标是全文结构、跨页续文/表格、表图所属、原序与跳号说明，并同步隔离工作台。没有要求 Items、Snn、符合性分析或 Excel。

这是共享宿主、每格一次的结构阶段探索，不是完整提取基准。600 秒是本局部探针的观察预算，不能据其截止宣判模型最终完成能力；完整流程仍遵守完成能力与效率分离的评测约定。评分规则在查看新成果前冻结，以原件及公开业务规则核对，不按旧节点数量或旧 ID 当标准答案。HTTP 同步与实际浏览器渲染分别记。

|---|---:|---:|
| 首个有效 Map 保存 | 438.939 秒 | 301.758 秒 |

两格均有 5 次工具实际返回图像。次数按 item ID 去重，不使用旧 runner 中将 started/completed 双计的字段。两份已保存 Map 均与各自 API 一致，冻结程序评分各 31 PASS、0 FAIL；2 个自由文本表角色保留程序 REVIEW，新版独立回源审核确认其语义合适；不改评分器将同义描述强行按旧拼写判错。两格的完整程序/语义核对报告保存在 evaluator。单次观察提示新入口有用，尚不能给稳定加速比例，更不能把旧接口截止当作 Luna 最终能力不足。

新版剩余 10 次 MCP 失败均在读取：5 次逐页材料未 prepare、3 次表片段读取缺 capture 版本、1 次 max_chars 超界、1 次 image 请求缺 page；另有 1 次自写 jq 误用字段。没有 Map 编译失败。这些是下一最小增量的证据：准备状态、带版本的回读句柄、当前来源定位和响应预算应尽量由工具承接，不能继续要求 Agent 机械记忆/拼接。版本校验和语义歧义保护仍要保留。

主 Agent 在模型结束后实际打开工作台，选定具体外部任务，看到 v1 结构树、完整 5×3 配置表、合并首行、全部三项部件、原 PDF 第4页和精确框，以及 2.6→2.10 来源提示。此后验记录在 `browser-check.json`，不回写模型本身的 `BROWSER_RENDERING_NOT_VERIFIED`。

同时发现：通用 project/document URL 会落到未开始的原生工作，需具体 work/revision 链接；模型终稿称已经视觉确认缺号，但持久化提示仍“待回查”。后者不是编号已修复，而是自查处置未传到消费者。已与 UI 任务协调并登记到[接入关注项](实体任务工作区-UI多任务接入.md)，本轮未修改界面或伪造处置反馈。
