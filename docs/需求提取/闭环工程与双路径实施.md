# ReqPilotX 闭环工程与双路径实施

更新：2026-09-06。依据用户本轮方向调整。执行顺序由[开发计划](开发计划.md)统一维护；本文解释产品链路、复用边界和可验证的交付条件。

## 当前决定

最近的案例工作同时承担了需求澄清、样例标注和交互验证。已有反馈足以建立第一版粒度口径，不再以逐条人工认可或全文精度趋于完美作为闭环开发前置。
以后由Agent依据现有反馈继续阅读、自查、修订和回归，用户主要处理重大歧义、原则冲突、缺失输入及正式客户承诺。未核对不等于未保留，也不自动等于必须用户点确认。

这里的loop engineering指工程闭环：观察真实失败与用户反馈，定位证据/语义/工具/展示问题，实施最小修订，验证后保留版本，再用不同原文范围检验。不是模型自我打分多跑几遍，也不是仅把每条反馈加入更长提示词。

## 一条业务链，两种生产候选的方式

```text
客户SOR + 用户任务目标
  ↓
来源登记：原文件、身份、页/段/表格证据
  ├─ 辅线：快速代码拆解
  │    原生文本/布局/编号/逻辑表 → 快速结构候选
  │    不调用Agent；明确扫描/复杂结构缺口，不假装精细语义已完成
  │
  └─ 主线：Agent + ReqPilotX skills + 按需工具
       阅读 → 完整原文条目 → 分类/关联 → 必要派生 → 自查/修订
                      ↓
             同一原文树、内容/PDF、版本与反馈
                      ↓
             需求评估工作台：适用性、澄清、待证据
                      ↓
             工程师响应：接受/有条件接受/偏离/待澄清
                      ↓
             版本化Compliance Matrix / Excel草稿与交付
                      ↑
       反馈 → Agent判断影响范围 → 局部修订 → 同源回归与差异
```

响应状态词先作为产品工作词，具体Excel字段和状态映射以实际交付验证收敛，不先扩建状态机。
目前没有内部知识库，故自动技术符合性结论保持待评估。流程仍可完成客户原文提取、问题归集、人工响应、保存和草稿导出；不能以没有内部库为由无限期推迟整条业务链。
后续接入内部证据时补强判断依据，不重新定义来源和Matrix行。

## 粒度已清楚到足以开工

最小分析单元不是最短句子，而是能让工程师给出不掩盖差异的清楚判断的内容单元。

- 原文父项完整保留；派生项是可选的分析视图，不取代客户原文。
- 一个目标的参数、条件、设备、方法、样品状态与判据保持成组。多个数字不自动产生多项要求。
- 不同义务、适用分支、责任、接受结果或证据路径在合并后会被掩盖时，才进一步分开。
- BOM按业务分支保留内部结构；项目矩阵/依据清单保持完整；表注可有独立语义。DVP的一次试验可跨多行/多页。
- 分类、主题、内容角色、适用状态、可分析状态分开，不因待定义而删掉需求类别，不因方法或标准名称自动归约束。
- 原文标题/编号优先；Agent概括、建议及派生表达显式区分，派生可定位到准确原文。

这些原则采用[规则V1](分类与验证关联规则V1.md)与已收到的补充反馈。具体新案例仍可能有分歧，但不再反复重开全部上层分类。

## 现有能力与真实断点

| 部分 | 已有可复用内容 | 下一步处理 |
|---|---|---|
| 来源读取 | PDF/DOCX/XLSX适配、原生文本、表格、图像、定位和渲染 | 用薄的调用入口提供基础捕获与可选增强，不重建解析器 |
| 快速代码路径 | 大量解析与结构逻辑；历史高保真、增强、门禁耦合 | 独立测量基础捕获耗时及缺口；普通可恢复缺口形成部分候选，来源错绑/损坏仍阻止发布 |
| 用户语义 | 规则V1、真实反馈、PDS连续工作版与已认可范围 | 进入工作Skill和有代表性的回归；停止不断增加私有材料化脚本 |
| 旧Agent Kit | 0.15.2工具、schema、stage transport和验证资产 | 旧分类和固定阶段口径与当前需求不同，暂作兼容资产；不能原样当成新主线语义入口 |
| 主应用核对 | 原文树、内容/PDF、表格、派生依据、筛选、反馈、原序Excel | 当前读固定工件；接共享发布/版本切换和反馈回流，保留有效界面 |
| 当前Agent入口 | `.agents/skills/reqpilotx-extraction-loop`及共享反馈读取工具 | 已能读取当前/历史反馈并通过baseline_loop材料化本地新版本；尚未自动调度、生产发布或完成独立复现 |
| 下游业务 | 主应用已有分析/人工决定/Matrix相关源码 | 新候选→人工响应→导出尚未以同一真实任务验证，优先打通此段 |
| App Server | 协议、工具宿主、生命周期、结构化输出适配 | 复用传输能力，改为承载同一任务与技能；不把旧canary运行策略直接当产品会话策略 |

暂不删除未证明无消费者的旧代码。本轮是改变主线入口与复用方式，不是把整个旧管线重写一遍。

## 主线的最小闭环

一个真实任务至少能：

1. 从客户文档或已授权的固定来源开始，明确提取与派生范围。
2. 加载当前Skill和可用工具，形成有源可查的候选与少数关键问题。
3. 在现有主应用中查看、反馈；反馈保存后Agent能读取正确的版本和对象。
4. Agent仅修订受影响范围，保留原文/已认可结果，展示新旧差异；不要求逐行确认才能继续。
5. 从同一版本进入人工逐条响应；没有内部证据的自动判断保持待评估。
6. 导出同一响应版本的Matrix草稿；原文、派生、条件、偏离、未解决项可以追溯。正式客户响应由工程师确认。

共享工具接通第3项中的“应用反馈→Agent输入”；baseline_loop已实跑第4项的本地修订、来源保留和差异，形成[六份B1](多文档提取基线B1.md)。工作Skill固定第2–4项的行为方向。
**尚不能声称上述六项全部已打通。** 紧接着的实现重点是通用候选发布/版本恢复，以及第5–6项的人工响应纵向连接。

## 快速路径的定位

快速路径用于低成本、低等待时间的初步文档整理，也可作为Agent可选择的工具。
它与Agent主线共享来源、定位、原文对象、主UI、反馈和导出，差异集中于候选如何产生及其可信范围。

基础层先完成文本、编号、布局和表格事实。视觉增强、难表恢复、深度语义分类和严格细分按需执行。
纯代码不能靠无限关键词补丁保证语义边界与分类质量；不确定时保留内容和可解释缺口，交给人工或Agent继续。
先在原生PDF与复杂表格上测量基础耗时、原文遗漏/错序和人工修正量，再决定具体删减或封装哪段代码。

## App Server迁移边界

业务Skill、来源/候选/反馈/响应工件和工具合同保持；迁移的是宿主调用与持久会话。
App Server负责线程与轮次、工具调用、事件流、授权响应、打断和恢复；ReqPilotX负责业务对象、来源事实、有效人工决定和交付版本。
持续在线意味着任务、成果和反馈可以持续接续，不意味着模型必须不停推理或空转。

官方协议提供Skill显式调用、`skills/list`、`turn/start`、`turn/steer`、`turn/interrupt`及恢复能力，适合嵌入现有应用。[OpenAI App Server文档](https://learn.chatgpt.com/docs/app-server)
现有适配仍需按安装版本验证字段和会话生命周期；当前没有新建远程模型轮次或完成主线App Server迁移。
其它Agent宿主可以先通过相同CLI/工具及文件合同接入；格式兼容不等于效果等价。

## 如何判断loop在改善

核心看关键遗漏/错归属、用户实际修订量、首个可用草稿耗时及工程师核对时间。条目数、测试数、模型一致率和确认按钮次数不能代表产品质量。

把失败区分为：源事实错误、当前案例语义错误、可复用原则缺口、工具/合同错误、展示问题。一次反馈先做最小影响修订；只把可推广且有证据支持的部分沉淀为公共规则。
同例回归证明没退化，新范围/新文档检查泛化；不需要每轮都让用户重新标注已对齐的案例。
