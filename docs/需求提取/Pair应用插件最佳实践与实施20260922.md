# 业务应用作为DSH插件：参考实践与ReqPilotX落地

2026-09-22。本次跨DSH、Backstage、Grafana、VS Code、MCP Apps、Tauri及长任务API模式检索，下面只采用官方文档和维护者仓库作为实现依据。检索是有范围的工程调研，不宣称穷尽全网或存在一个通用于所有宿主的“最佳插件”。当前开发基线是新repo的R1–R6架构，不重做已完成的工程迁移。

## 结论与形态

ReqPilotX适合“独立业务能力＋宿主应用插件”的组合：`packages/engine`、`apps/server`、`agent-assets`和`packages/workbench-ui`分别维护业务、服务、Agent资产及界面，`integrations/pair`只处理DSH运行和交互差异。DSH的npm/Cordis Bundle、Host、Client机制继续作为正式接入方式。

用户说的“SaaS通过plugin接入平台”在集成关系上成立；当前ReqPilotX默认是Pair管理本地服务，远程SaaS会是另一种部署形态。远程租户/身份/OAuth尚未实现，不能由本地插件入口推断已经具备。采用以下模式不需要换框架或在Pair复制整个业务实现。

## 对现状的判断

R4已经将Pair运行切换到显式、非editable的engine/server安装，独立Web产物以及真实子进程验证；9月14日“仍靠开发目录找Python”的记录不能再当作当前缺口。共享UI/API客户端与构建版本检查也已有实现。

现存重点是：任务发起/work-session绑定、真实进度、动态地址恢复、完整交付和正式分发。还需要补远程认证/文件通道、异常进程恢复及新机器安装；当前原文PDF查看仍使用本地服务origin，不声称已具备远程SaaS隔离或认证支持。

下一步的工作对象应明确分开：

- 应用身份：一个持久业务存储的宿主连接身份；不是账号、租户或Pair Session。
- 运行实例：每次进程启动的身份，可随重启改变。
- 业务工作：沿用共同task/work与原件hash、能力包完整bundle identity。
- 查看成果：明确revision；UI和Excel使用相同版本。

这样更新能力包或改变服务端口不需要重新解释业务身份。端点变更仍必须按既有binding校验重连，不能直接改封存任务上下文。

## 本轮已实现：稳定身份与能力发现

`integrations/pair/host/src/application-discovery.cjs`定义`reqpilot-application-host/v1`。这是宿主连接合同，不是第二套业务schema或MCP Apps协议实现。Host与Client构建消费同一份模块，构建回执记录该模块hash。

- `/reqpilotx/config`从白名单投影状态、应用/进程身份、地址及已实现操作；运行目录、凭据、安装详情和原始失败正文不直接输出。
- managed模式应用身份来自持久owner记录；进程instanceId和serviceOrigin独立。只读connect未验证远端身份，故不伪造稳定应用ID。
- 当前项目/导入/成果读取能力按就绪情况声明。Agent start/resume/cancel及真实事件能力明确为false；READY只代表服务可用，不代表模型或语义验收通过。
- 接口协议、必要能力字段或managed身份缺失时，Client明确报告不兼容；不静默猜测可用功能。
- Host身份使用稳定applicationId，传输客户端身份仍随origin变化，使旧请求失效；Catalog不再用每次启动的instanceId作为业务组件key。
- 写入口策略与能力发现共用操作声明，服务未就绪时已有POST返回503；不因暂不可用误报功能不存在。不扩大允许写入的路径。

这不是完整会话恢复：当前文档选择、已运行任务及断线后的精确恢复仍需业务绑定和事件层实现。
