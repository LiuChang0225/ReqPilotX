# 模型阅读效率：可复用方法与验证

更新：2026-09-10。回应用户关于模型低效、方法复用和 skill 封装的追问。

后续实际进展见[历史方法重验与读取闭环首轮](历史方法重验与读取闭环首轮.md)：同源历史方法已重新运行，当前Agent完成选定页/局部检查，逐页工作区及原生读取改进已随r16安装。本文保留此前JSON投影对照与审计时入口状态，不能将下表全部当作当前仍缺失的能力。

## 结论及适用边界

可以把有效工作方法封装为共用程序和短 skill，让 Luna 少做机械工作、少走错误路径。本轮已经证明紧凑读取可以减少数据量，并保留捕获结果的内容与关系；尚未证明 Luna 的语义质量、总时间或成本已改善，更不能承诺与更强模型效果相同。

此前两轮 Luna max 有 1,507 次读取调用。原因包括读取大量底层字段、重复扫描整份节点数组、提前加载后续阶段说明、错误后重做；也有当前入口的接入与契约问题。详见 [Luna 实测](Luna-max-r15实测.md)。现有 PDF 坐标、局部裁切、表格定位和文本条目字符范围能力确实存在，不能统称为“坐标能力缺失”。本轮阅读包只证明优于巨型原始 JSON 的读取方式，尚未与已验证的逐页 Markdown/高清页图方案作同源对照。

## 历史方法及当前入口核对

用户追问后重新核对了历史记录、现存代码和实际工件。此前已经总结并运行过“全局观察—局部精读—回看原页—修正判断—局部恢复”，记录见 [Codex App 全文理解能力根因与重建](../archive/2026-09-03/需求提取/Codex%20App全文理解能力缺失根因与重建记录.md)。历史 PDS reference 为 29/29 页高清视觉检查，同时使用逐页 Markdown、TableIR JSON/HTML、图片资产和原 PDF；后续也真实验证了领域 skill 与官方 PDF skill 的组合。历史状态不自动代表当前入口可用，但这些已验证方法应作为能力迁移的对照。

| 层次 | 已有实现与证据 | 当前 Luna/r15 入口 |
|---|---|---|
| 原文阅读工作区 | `reference_workspace.py` 生成 `pages/Pxxxx.md`、页索引、2倍高清页图、contact sheet、表格JSON/HTML、图片及placement索引；PDS v6私有工件仍有29份MD、29张高清页图和30份表格HTML | `capture_fast_source` 生成SourceIR、原件、资产、书签、批注及算法候选；本次capture没有逐页MD或高清页图目录 |
| 视觉工具 | `pdf_source_crop_renderer.py` 支持真实bbox、页面几何及可选scale的局部裁切 | `reqpilot_read` 可读取原PDF页，但固定1.5倍渲染；未向该Agent暴露已有局部crop/scale参数。两轮实际页图读取仅P1 |
| 官方PDF能力 | `agent-kit/.agents/skills/pdf/`及来源/版本/SHA记录仍存在，历史有实际多skill运行证据 | 当前任务只自动注入`reqpilot`入口，冻结包可读的五个skill均为领域skill，不包含官方PDF skill |
| 块内归属 | 既有条目模型接受`start_offset/end_offset`；旧Map scope也有source span合同，但不能仅凭字段存在宣称所有块内组合都已闭环 | 当前插件`compile-map`按完整source handle独占归属，没有把字符区间接到Map输入；问题是阶段/适配合同未复用完整 |
| 表片段行号 | SourceIR保留真实单元格行列、span和bbox，现有程序验证行覆盖 | 插件选取`[lo,hi)`行后仍传原表`row_count`和全局行号，下游按`0..row_count`要求覆盖；因此局部片段被误报漏行。应修转换/验证合同，不重做PDF坐标提取 |

这里应将“阅读工具”定义为同一来源绑定的可读证据工作区及访问能力：逐页原文、整页/区域像素、完整表格关系、图片资产、精确位置与真实阅读状态互相对应。新增`reading-packet`只是其中的紧凑SourceIR辅助视图，不生成逐页MD、高清页图或视觉理解，也没有调用旧工作区生成器。

能力复现测试与日常自适应读取须分开：既有reference方法要求实际检查每页高清图，contact sheet只作导航；不能在未证明等价前，用“仅查怀疑页”替代后仍称为能力复现。图片已生成、工具已返回、Agent已读和语义已验证也应分开记录。本次99段验证属于程序读取完整性，不属于Luna视觉或语义验收。

## 我会怎样做，以及怎样交给低能力模型

| 实际方法 | 程序承担 | skill 承担 |
|---|---|---|
| 先获得可读、可定位的原文，再判断 | 复用逐页文字、高清页图、表格/图片索引及精细来源定位；紧凑JSON作为辅助读取视图 | 本轮能力复现需实际逐页视觉核对，再按歧义放大或回查；日常自适应策略另行验证，不把预览当已读 |
| 每次读取有明确问题 | 返回确切路径、范围和记录数 | 先明确是要判断标题、表归属、编号粒度还是图意，再读取对应证据和案例 |
| 已读成果可续接 | 源文件摘要、不可变阅读段、已有 candidate 写入工具 | 分开记录已读段、实际页图检查、未解决范围、当前候选和下一步；来源未变就复用，反馈只重查相关范围及上位条件 |
| 编译失败时做局部诊断 | 共享编译器检查覆盖、定位和身份 | 只读相关契约，局部修复；同错且无新证据时用最小诊断确认能力缺口；不为通过校验删除封面角色或合并无关章节 |
| 同版结果直接交付 | 沿用内部程序导出 Excel | 检查实际阶段成果；不让模型重新读取 Excel 全文再做一套分析 |

普通编号条款先读完整正文与上位标题；编号 BOM 先核对表头、合并格和注释再决定整体处理；页面大表内有多个标题时，查看原页并确认业务所有者。案例由实际歧义触发，不要求所有 reference 每次全读。必须同时保留完整源内容、来源关系和未读/不清晰范围，不能以摘要替代全文后把速度提升当作质量提高。

主 Agent 能临时写 Python，而此前 Luna 的原生工具不开放通用执行；直接比较两者并不公平。本轮新增 `reading-packet` 共用命令并接入原生工具入口，让同一方法不依赖主 Agent 的额外权限。它不调用模型、不预先填写正确 Map、不分类、不去重、不解释图片。

## 同一份真实原件的确定性对照

使用与 r15 测试相同的 34 页 Oil Pump PDF 捕获结果。比较的是原来被逐窗读取的完整节点数组，与新阅读包。新包额外包含捕获元数据和资源记录；不是模型 token 或全流程耗时对照。

| 指标 | 实测 |
|---|---|
| 原节点数组 | 6,156,705 字节，231,972 行；原保存文件另有末尾换行 |
| 新阅读包 | 2,559,321 字节，4,854 条记录，99 段；字节减少 58.43% |
| 内容与关系 | 1,689 来源块、3,141 单元格、26 图片出现位置、23 资源保留；包含全部节点/单元格原文 |
| 完整性验证 | 按声明引用恢复 PDF 行坐标、还原重复定位后，整个 SourceIR 模型相等；原捕获文件未修改 |
| 原生读取接口 | 99 段逐一读取全部成功，最大响应 33,572 字符；无二次大文件转存、无超大单记录 |
| 读取调用的可比下限 | 旧节点数组按每次 500 行至少 464 次；新包可用 99 次段读取完成。均不含生成/索引、页图、精细坐标回查和语义工作 |

阅读投影省略空字段，将相同的 visual locator 声明为 native locator 的别名，PDF 行级坐标仍可通过确切 SourceIR 指针取得。节点和单元格的原文、空字符串、合并区域、表头、注释、公式、图片关系不变。程序不解决原始捕获漏字，也不证明 Agent 已经读懂。特别长的单记录完整保留并标记 oversized，仍需进一步按字段读取；不宣称所有输入都能单次返回。

机器证据在忽略目录 `prototype/runtime-data/luna-max-r15-test/compact-reading-proof/`：`verification.json` 和 `native-reader-verification.json`。可复现核对工具为 `prototype/scripts/verify_source_reading_packet.py --manifest <reading-manifest.json>`；实际模型回合没有启动。
