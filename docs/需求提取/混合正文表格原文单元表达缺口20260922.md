# 混合正文与表格的原文单元表达缺口

2026-09-22。来自Pair合成文档实跑及冻结包6e55cff…的独立只读审计。本记录描述已复现的合同缺口与待实现切片，不把设计写成已交付功能。当前业务定义仍以[模型V1](文档结构与原文条目模型V1.md)为准。

## 最小案例与结论

一条编号规定“交付总成应包含下列完整BOM”，后接整张零件清单；零件内部有1/2序号。它构成一个组成义务，正文和表格应在同一个业务单元内保留。当前工具可以整表保留，但实跑把引导正文和整表分别生成SRC/REQ，重复计算业务义务。

原文不能因工具限制被改成标题/非业务内容，也不能为了减少行数丢掉正文。模型判断、程序可表达性、全覆盖与交付报告分别核对：完整源文保存或程序检查通过，不证明业务粒度正确。

## 冻结工具的确切限制

1. Map的logical_tables只接受owner、标题、角色与表格片段，没有直接拥有正文的声明；正文被保存在owner node.source_content。
2. scope准备会把owner正文暴露给表格scope，同时对非空正文再生成独立text scope。
3. TABLE_RECORD已有shared_source_content_ids，可将正文作为显式共享上下文读取和展示，但共享引用不是所有权，也不会覆盖该text scope。
4. text校验要求非空正文落到文本条目或合法纯标题。义务句不能归structure_only；不处理该scope会留下unprocessed_scope_ids；另建文本条目必增SRC。
5. 当前记录校验限制表格、正文、图片直接绑定互斥，coverage atoms也不计共享正文为拥有内容。

因此，在本冻结合同中，完整保留来源、全文scope覆盖、单一混合BOM条目三项不能同时满足。Map-only重排不能合法规避：evidence_refs不提供所有权；标题或NON_BUSINESS/DUPLICATE_CAPTURE并不符合该原句；物理行范围也不包含表前段落。

## 修复切片与验收

| 部位 | 需要落实的行为 |
|---|---|
| 明确所有权 | 提供source-bound owning_text_refs（在Map或Items哪层声明须经实现对照后确定），区别于可多处引用的共享上下文；Agent明确选单元，程序不凭相邻位置自动合并 |
| 条目模型 | 一个TABLE_RECORD可同时拥有正文绑定和表格片段；保留原文语言、条件、编号及各自坐标；不新增第二REQ来承载引导句 |
| scope与覆盖 | 以精确范围登记正文所有权，能明确说明某text范围由哪个混合单元处理；不静默吞scope，不重复拥有，不借shared字段绕过校验 |
| 编号与原序 | 源编号归完整单元；排序依据真实首个来源位置；不再以“只有文本记录才能拥有标题编号”阻止合法混合条目 |
| UI与导出 | 同一条目显示正文＋原表；表格仍是表格。台账、分析单元数、来源定位与Excel一致，避免双计数 |
| 修订 | Map重绑、局部修订、视觉校正与引用保留全部组成；失去任何被拥有范围时明确报错 |
| 兼容 | 旧工件保持原始hash与内容。优先复用既有绑定字段并审计序列化；若需协议升级，配套发布引擎/服务/能力包，不让旧消费者静默丢字段 |

最小回归应证明：上例只有一个完整组成义务；另一个独立编号义务不会因同页同表被吞并；两个产品变体各有完整BOM时可保留两个单元；共享定义可以被多处引用且不变为所有权。程序编制→source read→coverage→局部修订→UI snapshot→Excel要贯通，不能只改计数器。

## 跨版式语义验收

评测线2026-09-22补充的简化建模建议：区分结构、原文条目与工程派生；边界核对关注并列事项、同项组成、适用上下文。该建议尚未实现或重新评测，不替代现行产品合同，也不将其宣称为新的已验能力。

在上述四组正反例之外，增加同一内容的版式变体：段落、表格、跨页续表/续文。只改变版式、不改变原文含义与关系时，业务单元、组成归属、共享引用与有效编号的拆分边界应保持一致；页码、坐标等定位随新原件重新绑定，不能复用旧坐标。完整BOM及同一试验的方法/条件/判据保留整体；独立编号义务、不同里程碑事件和各自完整的配置仍分别核对。

验收逐项比较完整内容、支配条件、例外、组成关系、来源定位及UI/Excel呈现，不只比较SRC/REQ数量。不得通过把义务降为非需求、取消有效编号或隐藏重复条目来凑出目标数量。
