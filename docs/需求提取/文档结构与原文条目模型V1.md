# 文档结构与原文条目模型 V1

状态：**CURRENT / ACCEPTED PRODUCT MODEL**。采用日期：2026-09-07，依据用户在行业模型对照与关系说明后明确要求“固化下来”。

2026-09-09 用户明确补充：原文有序号默认递归拆到最低层，完整 BOM 等共同分析单元例外；表内嵌图不改变其表格业务身份，前端与 Excel 采用同一实际对象状态。以下已纳入该补充；旧工件不因规则文本更新而自动重签或重判。

适用范围：客户文档理解、Document Map、原文条目、需求拆分、工作台与 Compliance Matrix。本文定义这些对象与关系的当前产品含义；分类口径继续以[分类与验证关联规则V1](分类与验证关联规则V1.md)为准，开发顺序以[开发计划](开发计划.md)为准。本文不是所有实现与既有案例均已验收的声明。

## 1. 四个独立维度

| 维度 | 表达什么 | 示例 |
|---|---|---|
| 组织位置 | 原文对象属于哪里，前后怎样排列 | 文档、章节、子章节、条目及其原文父子关系 |
| 内容形式 | 原文由哪些可核对的内容组成 | 文字、列表、表格、图片或混合内容 |
| 内容判定 | 此原文条目是否独立评审，以及其业务含义 | 需求/非需求、需求类别、非需求内容角色、主题 |
| 来源与关联 | 对象来自何处，怎样派生，分析还需读取什么 | 原文绑定、派生依据、引用、共享上下文 |

上述维度不能合并为一个互斥枚举。“表格”不能代替需求/非需求判断，“文控信息”不能代替结构类型，“派生”不能成为第三种内容判定。需求类别、内容角色和主题各自独立。

一个对象可以同时承担结构位置与原文条目身份，其正文又可以包含文字、表格和图片。UI或Excel中的“结构类型”是便于阅读的组合标识，不是完整底层模型，也不能驱动重新分配父级、制造条目或重判分类。

## 2. 原文组织：有序、递归、允许直接内容

下面列出允许的组织方式，不要求每份文档具有所有层级：

```text
文档
├─ 文档级原文内容                 ← 可以没有所属章节
├─ 章节
│  ├─ 子章节                     ← 可以继续递归
│  │  ├─ 原文条目
│  │  └─ 原表
│  │     ├─ 表格条目 A
│  │     └─ 表格条目 B
│  ├─ 原文条目
│  │  └─ 原文子条目              ← 仅当原文确实如此组织
│  └─ 原表／图片等内容
└─ 其他章节或原文内容
```

- 文档可以直接包含内容；章节可以同时包含子章节、正文条目、表格和图片。不补造缺失的中间层。
- 章节深度只表示文档组织，不能机械决定需求等级、需求类别或系统/子系统分配关系。
- 每个原文组织节点在该文档视图内有明确所属父级及顺序。引用其他范围不改变原文所属父级。
- 仅为回查保留的页框、表片段等来源证据，不自动成为业务表、条目或已处理覆盖。它与原文中的业务引用分别表达；真实业务表及其合理子条目仍保留原有包含关系，不能因同源重叠而一律删除。
- 原件补读可产生带方法、原始位置与可见性说明的新来源观察。旧原件和捕获版本保留，新增观察必须能够追溯并核验；文本对象存在、像素可见与业务语义正确是不同事实。具体版本须按已保存内容与哈希绑定，不能只凭基座捕获ID认定相同内容。
- 视觉文字/表格观察可通过显式来源引用投影为同一Map/Items可编制节点；原生捕获、原始OCR与Agent回图纠正分别保留，纠正记录来源和lineage，不覆盖旧观察。表格行列、合并和可用单元格坐标随同保留；OCR介质不改变业务对象形式或自动决定分类。观察可编制、文字正确及工程师接受仍是不同状态。
- 文档单元按实际来源识别，不等同于文件扩展名或物理页。独立附件文档可以与主文档平级；真正属于正文的附录按原文归属保留。独立试验大纲不能被塞进虚构的主文档章节。
- 原文已有编号、标题优先保真；无编号正文可以形成条目。辅助显示标签须标明来源，不能升级成客户标题或原编号。

## 3. 原文条目与内容形式

SourceItem / 原文条目是来源忠实、可独立检查和处理的业务范围，可以是需求，也可以是有意义的非需求。全部原文条目分配SRC，需求子集另有REQ，原文编号独立保存。纯标题保留为结构节点，不为增加计数再复制一个非需求条目。

“文字条目”“表格条目”“图片条目”可以作为阅读标签；一条原文条目也可以同时拥有文字、列表、表格和图片。完整试验中的设备、样品状态、方法、条件、判据与图示可以共同组成一个条目或通过明确关联共同参与评审。

**1:1共用一行，1:N才展开多个业务条目。** 一个完整的“4.1 标题＋正文”可以同时承担层级与条目身份，不再生成“4.1 → 4.1正文”的重复壳层。整表恰好构成一个条目时，也不生成“表格 → 同名整表条目”的重复层。后台可以保留各自必要身份和来源绑定，界面不必为每个内部对象增加一行。

| 原表语义 | 原文条目组织 |
|---|---|
| 整表共同表达一个完整事项 | 整表作为一个条目，与表结构共用一行 |
| 多个完整试验 | 保留总表及多个试验条目；每项可跨行、跨页 |
| 两个完整BOM产品分支 | 两个分支条目；零件行作为内部结构和证据保留 |
| 某条要求的参数表、条件表或图示 | 留在该条目的内容或关联上下文中 |
| 独立表注、说明或约束 | 依据实际含义形成条目并关联原表，不机械并入邻行 |

物理行、列、单元格、图片和业务条目不要求一一对应。仅列出测试项目的矩阵不因有多行就成为多条完整试验要求。表格分支是本产品的来源范围表达，不是所有文档必须具备的结构层级。

### 3.0 封面、目录和文控整体

封面、目录等导航/文控内容按完整来源块组织，保留文字、版式、表格、图像和定位，不按封面字段、目录标题/页码或目录条目中的章节号创建SRC/REQ。目录中的“4.1/4.2”是指向正文的导航，不是正文原编号拆分的输入；正文相应条款仍独立识别。完整块在树、详情和Excel中可阅读，不能为了不发SRC而丢弃原文。修订记录/签批表等文控内容同样先按整体判断，不机械逐行识别。

这一规则按已识别的内容角色适用，不以“第一页”或标题关键词删内容。若封面或前置页还载有独立保密义务、适用约束或交付要求，该实际正文范围仍须单独判断，不能因所在页是封面而隐藏。既有错误SRC通过显式版本修订退役与追溯，不在展示层静默删号。

### 3.1 原序号的默认边界与整体例外

**正文原文有序号，默认沿原序号递归识别到最低层。** 封面/目录等导航文控块先按3.0整体处理。 有意义的叶级正文分别形成原文条目，纯标题仍为结构节点；父条款自身正文、共同条件与作用范围保留。原文的 4.1.1、a)、试验号等须先辨明真实含义，不能把页码、尺寸数字、OCR 误识别当作条款号。

只有几个编号内容共同构成一个完整可独立分析事项时才保留整体，例如一份 BOM、一个完整试验的方法步骤或一个完整规格的参数集合。该决定须保留组合范围、全部内部编号/顺序/组成关系及成组理由；“同页、同表、同一标题”本身不足以例外。多个各自完整的编号试验默认分成各项，不能用整表例外合并。

原编号拆分是恢复原文包含关系，不自动产生 Snn，也不自动判为需求。没有原编号的复合条款，仍按完整原文条目及必要显式派生处理。详细边界见[PDF处理策略与粒度正反例](PDF处理策略与粒度正反例.md)。

### 3.2 混合内容的主类型

主显示类型由实际业务对象及包含关系共同确定。原表或表格条目内嵌图片，仍以表格/表格条目呈现，图片作为其内容或明确关联资产；不能因存在图像引用就改成独立图片。扫描表的来源载体是图像，其业务语义仍可以是表格。独立插图按原文独立组织；一个条款内有小表也不必把条款整体改成表格。

原图、图像释读和工程派生分别记录。释读可解释图中可见关系，推断须表明依据与不确定性，不自动成为原文需求。共用主类型规则不能掩盖上游对象本身误判，发现类型冲突须回到来源归属修正。

## 4. 三种关系分别保存

| 关系 | 含义 | 约束 |
|---|---|---|
| 原文包含关系 | 客户原文怎样组织 | 忠实保存原始所属、顺序、编号及层级 |
| 需求派生关系 | 从完整原文需求形成哪些独立分析对象 | 显式保存父项、派生类型、精确依据与身份，不改写原文树 |
| 引用／上下文关系 | 理解或评审此项还需读取什么 | 保存引用目标、适用范围与读取状态，不因关联改变父级或扩大义务 |

派生项可以在阅读树中显示为子条目：

```text
原文条目 SRC-012 / REQ-012
├─〔派生〕REQ-012-S01
└─〔派生〕REQ-012-S02
```

这与原文已有的“4.1 → 4.1.1”分别记录：前者是需求拆分成果，后者是客户原文组织。完整原文父项保留；只有业务需要且在授权范围内才派生。独立条件、参数、设备或方法的locator不自动意味着要新建派生需求。

当前需求拆分服务于独立分析和逐条响应；系统/子系统设计要求的工程下传与分配，不因文档层级存在而自动发生。共享表头、共同条件和相关原文通过引用读取，不在每个子项反复复制。

## 5. 统一应用与导出

- 提取、UI和Excel消费同一来源顺序、对象身份、分类及关系；导出不生成第二套语义规则。
- 同版本、同范围的UI和Excel共享父级、主显示类型、原编号、SRC/REQ、派生、释读及有效响应状态。筛选/折叠只影响阅读范围，不改变对象身份；导出全量或当前筛选须明确，折叠不默认排除内容。
- 正常Excel由内部程序基于同版本结果写出，不新增模型全文阅读、重提取或重分析阶段。导出故障按来源映射、状态读取、共同投影和渲染分别诊断。
- 已保存的定义/条件关联须在导出中可见、可定位。2026-09-14开发候选在既有“说明/待补充”列显示关联SRC与主表行并提供跳转，不改写原文或增加义务行；旧产物不回写，部署状态以开发计划和评测记录为准。仅snapshot同版不能证明所有关系已可见。
- 大节点显示自己的原文标题、来源范围、原文/需求/非需求数量、原表数与评审进度；不将后代全文汇总伪装成该节点原文。
- 原文父项与派生项可以同时可见，实际分析集合独立计算。是否需要分析不能仅由“是否树叶”决定，也不能重复计算父项与其替代分析子项。
- 原表与主Matrix是同一对象的不同阅读位置，长表呈现方式不改变条目粒度；全文、图像、方法和条件仍可追溯。
- 规则采用、Agent候选、自动检查、来源语义核验、用户接受是不同状态，不以结构字段齐全证明提取正确。

## 6. 行业依据与实现边界

[OMG ReqIF 1.2](https://www.omg.org/spec/ReqIF/1.2/PDF)区分Specification、SpecHierarchy、SpecObject和SpecRelation：层级递归且有序，对象与关系分别表达；规范也允许表格内容及表内对象的表示。本文借鉴其分离原则，不宣称本项目已提供ReqIF writer。

[Windchill RV&S文档结构](https://support.ptc.com/help/windchillrvs/r13.0.0.0/en/IntegrityHelp/client_docs_what_is_a_document.mif-2.html)区分Document、Section、Content/Node，其Category允许管理员配置；[文档模型关系](https://support.ptc.com/help/windchillrvs/r12.3.1.0/en/IntegrityHelp/client_docs_what_is_a_document.mif-3.html)分别描述结构、引用和追踪关系。

[Polarion Document Parts](https://developer.siemens.com/polarion/advanced-concepts.html#document-parts)区分标题、工作项、表格和普通内容。标题在其技术实现中可以关联Work Item，不能据此认定客户标题属于需求。

这些依据没有共同规定一张固定的“文档→章节→条目→表格→派生需求”树。本文是适配ReqPilotX目标的产品模型，不将供应商产品的类别枚举冒充行业统一标准。

现有Document Map、SourceItem、SRC/REQ、内容绑定及显式decomposition已提供主要基础。2026-09-08新增`PARAGRAPH`表达普通无编号段落，与编号条款、原生列表、表格记录、表格分支及图片并列；文字编译、修订、台账与界面合同共用该值，旧工件hash不变。实际列表才用`NATIVE_LIST`，普通正文不再被枚举强迫误标。图文混合已可通过同源图片/共享上下文关联完整读取。2026-10-01开发切片允许一个表格原文条目明确拥有正文精确范围：表格候选的`owning_text_spans`与文本scope的`table_owned_spans`必须双向吻合，混合记录同时保留文字和表格绑定，局部修订同时处理两个scope。共享上下文仍不取得所有权。旧工件缺省字段不进入原序列化，hash不迁移。独立应用自动窗口任务让表格与正文边界分别声明同一精确归属并在同一次产品基线发布中校验。一个节点有多张逻辑表时，先补齐尚未发布的同节点表格候选，再联合判定正文归属；先前已发布的范围保持不变。每张表的完整候选及窗口检查点均绑定原文、Map、请求和模型身份，正文阶段中断后无需重新调用已完成表格。重叠归属、来源变化或检查点损坏会在发布前拒绝，不自动裁剪或重分配文字；已发布正文的改挂仍需显式联合修订。整组只产生一次产品基线版本，UI/Excel共用该版本。合成回归不代表真实客户材料或 Windows 全链通过。

## 7. 后续修改的核对点

1. 无章节文档、章节直接正文、深层子章节均能表达，不自动补层。
2. 1:1条款/整表不产生同名父子行；1:N业务条目保持正确原序。
3. 文字＋表格＋图片共同表达的完整条目不被强制拆散。
4. 原文子条目、派生子项、跨章节引用分别识别，引用不改父级。
5. BOM分支、多行试验、仅项目矩阵和表注使用各自的语义粒度。
6. 结构、内容形式、判定与关系没有被一个显示枚举重新混合；原编号和稳定SRC/REQ不随视图变化。
7. 原编号默认识别到最低有意义层，整体例外可解释且内部结构不丢失；原文包含不冒充工程派生。
8. 含图表格、扫描表和独立图在UI/Excel保持同一业务身份，释读不覆盖原文。

SRC/REQ与来源排序的具体改进建议见[编号及显示顺序](SRC与REQ编号及显示顺序.md)。该方案尚未触发历史号码迁移。

## 2026-10-02 分析输入中的显式共享来源上下文

隔离集成候选已修复分析 packet 仅携带非祖先 `context_source_ids`、未读取被引用正文的缺口。共享内容及显式同原件来源关联现在展开为 `referenced_customer_context`：保留来源身份、原文、表格单元格、原生位置、图片及间接关联，并参与单元输入 hash；依赖发生变化时重评依赖单元，保留无关结果。有限图遍历记录循环，不创建额外义务。不存在、已退休或跨原件来源不能静默采用。

此展开只表达既有 Agent 明确选择的上下文关系，不自动决定适用性，不将客户矩阵中的历史响应当成本次判断。可选 OpenKB 内部依据桥接仍独立于客户来源提取，详见 [OpenKB集成候选](../../integrations/openkb/README.md)。原件证据检索、Agent判断与工程师正式接受继续分开；离线合成回归不表示真实模型或公司部署已验收。

## 2026-10-02 原生原件准备与模型分析状态

原生Web有限接入将登记原件的精确引用身份、完整摘录与native locator送入既有分析/工程师意见及immutable交付链。宿主生成的原件准备仅为待审候选，模型未运行时必须保留 `NOT_RUN` / `NOT_PERFORMED`，不能将它计为已执行AI分析或正式人工接受；继承的既有分析单元保持独立来源。canonical snapshot与“内部原件引用”工作表冻结同版引用回执，原文、来源SHA、packet/assessment/knowledge绑定可回查；引用本身不证明适用条件和完整覆盖。详见 [原生OpenKB有限接入](../../integrations/openkb/README.md)。
