# 主 skill 可理解性验证

更新：2026-09-11。用户指出主 skill 没有简单阐明需求，要求让新 Agent 只加载 skill 与任务验证理解。本轮执行理解测试并准备候选稿，没有把复述能力当提取质量，也没有替换已安装技能或运行工具。

## 测试方法

四个全新子 Agent，分别是原稿 Sol high、原稿 Luna max、候选稿 Sol high、候选稿 Luna max。全部 `fork_turns=none`，不传当前开发对话。业务输入只有一份冻结主 SKILL.md 和同一句任务：

> 请用 ReqPilot 帮我整理这份客户 SOR，用于报价评审，最后导出需求矩阵 Excel。

测试注明尚未附原件，只要求解释目标、成果、开始/继续方式、用户反馈和第一段用户回复；不执行提取。明确禁止读取其他 skill、references、项目规则、历史结果与评分材料。两版本使用相同提问，评分观察点事先保存，不提供目标答案。

这是独立子 Agent 的业务上下文隔离测试，平台基础指令与工具仍存在，不宣称操作系统级文件沙箱或独立 CLI plugin 行为验证。私有根 `prototype/runtime-data/skill-comprehension-20260911/` 保存原稿、候选稿、任务、rubric、版本哈希及实际开场回复；完整回复留在本次对话的子 Agent 结果。

## 实际发现

| 观察点 | 原稿 | 候选稿 |
|---|---|---|
| 能否说出服务报价评审、保留来源、程序导出 | 两模型都能 | 两模型都能 |
| 是否具体解释 SRC 与需求的关系 | 输出主要沿用术语 | Luna 明确区分定义/说明与提出义务的条目，Sol 明确完整原文与需求条目 |
| 开场是否明确没有内部资料仍可整理要求 | 两模型都未明确说出 | 两模型都明确说出；Sol 明确跳过符合性判断 |
| 是否承诺先给结构，再给条目 | 原稿解释有阶段，面向用户的表达较抽象 | 两模型开场明确展示结构后形成清单 |
| 是否已经人类友好且能正确执行 | 未证明 | 未证明；两模型开场仍带 SRC/REQ，Sol 还引入 Snn 授权问题 |

不能说原稿让 Agent 完全不懂。两模型都理解了大方向；但这不反驳用户认为它难读。原稿先讲抽象职责和协作边界，核心术语没有就地解释，方法、宿主字段和版本确认细节混在主入口。知道六步名称，不等于知道一条合格结果长什么样，也不能证明会及时交付。

原稿 Luna 开场要求提供原件，并“尽量说明文档版本、报价评审范围，以及可引用的内部标准或方案依据”。候选稿 Luna 则明确表示：“若还希望判断产品是否满足，请一并提供相关内部产品资料；没有也可以先完成客户要求整理。”这是可观察的表达差别，不是完整能力得分。

候选 Sol 直接询问 Snn 授权；候选 Luna 说只在无法确定授权边界时询问。2026-09-12复核发现，`reqpilot-review/SKILL.md`已明确完整流程请求可以授权必要拆分，无需逐项许可。因此此前把这点笼统列为新的待用户决定事项不准确，应把已有原则贯通到主稿/任务输入；已给授权不重复索要。仅要求结构或未覆盖派生范围的请求仍按实际范围处理，不能借改稿扩大任务。

## 候选稿怎么改

主稿由 3362 字符缩到 2248 字符，重点是重新组织内容：

1. 首段直接说明为谁做事、解决什么问题、交付什么。
2. 就地解释文档结构、原文条目/需求、派生子项，并给一条需求和一条定义的例子。
3. 明确先展示结构、再给条目；无内部资料时继续整理，跳过符合性判断。
4. 把五类需求用业务语言解释，保留编号、BOM、试验、表内图片等关键规则。
5. 具体命令、宿主字段与版本绑定放到按需工具入口，不在业务介绍里连续堆术语。

候选稿位于上述私有根的 `candidate-SKILL.md`。它是供人检查的草稿，链接按目标插件目录解释；理解测试不读取这些链接。原稿、候选稿及其结果分别保留，不能用新稿结果改写旧稿。

## 接下来的优先顺序

先把主 skill 写成清楚的业务委托：要求什么、成果长什么样、怎样继续、什么问题才需要人。再逐个检查职责 skill 是否同样明确，不只修改主入口标题。示例与工具协议按需展开；必要默认业务决定要显式定义。
