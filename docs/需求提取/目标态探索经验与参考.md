# 目标态探索：经验、反例与工程参考

更新：2026-09-04。范围：ReqPilotX阶段一的F06探索、范围纠正及典型案例目标态回合。

本文保存可复用的方法、已发现反例与适用边界。它不是客户需求原文、案例答案、已验收Gold，
也不覆盖[产品定义](../../PRODUCT.md)和[当前开发计划](开发计划.md)。
完整客户内容、逐条判断、截图和工作轨迹保存在私有运行目录，入口见[当前接续](active-context.md)。

## 1. 已经确认的开发方向

先让真实案例达到工程师可核对的状态，再沉淀可移植能力，最后接入统一应用。
当前最小技术链为：原文证据 → Agent语义决定 → 来源绑定工件 → 核对界面 → 反馈与修订。

- 原文与分析结果分层，换框架不应改变来源、业务身份或人工决定。
- 工具执行来源捕获、指纹/引用校验及结果组装；Agent承担语义判断和必要的回源复核。
- 原文条目、派生要求和反馈各有稳定身份，不能用数组序号、文件位置或页号代替业务身份。
- 现有解析器、数据库、App Server和前端是可用能力，不规定业务阅读顺序。

## 2. 证据等级必须分开

| 证据 | 可以说明 | 不能说明 |
|---|---|---|
| 来源字节与指纹匹配 | 分析绑定了选定原文件 | 文本层转写或语义理解一定正确 |
| 原生文本均有归属 | 捕获文本没有未解释的归属空洞 | 所有图片、图中小字、外部附件都已理解 |
| 工件检查通过 | 引用、坐标、身份及特定已知反例符合检查项 | 整个文档的语义准确率 |
| 浏览器交互通过 | 已测试路径能正确呈现并反馈 | 所有内容与所有使用场景已验收 |
| Agent代理复核 | 授权代理给出了有证据的推荐处置 | 产品负责人已经最终接受 |
| 用户明确验收 | 指定范围的业务结果/体验获认可 | 其他文档或宿主均可复现 |

不得把以上状态折叠成一个“完成”标记；报告必须说明范围、剩余问题和判定者。

## 3. 原文条目边界：按业务记录，不按版面碎片

### 观察

同一条款可能跨页，同一物理页可能含多个条款；同一业务行还可能跨页、使用合并表头，
依赖表外说明。按句号、行数、页数、单元格或模型窗口切分，会产生语法完整但工程含义不完整的记录。

### 可复用处理

- 先识别可独立核对的业务记录，再用字符/单元格覆盖校验检查有没有丢失或错归属。
- 结构标题只作标题；有直接正文时保留正文身份，但不重复造一个“非需求标题条目”。
- 原文父项保持不变，规范化派生另存。
- 重号、缺号、空白和待定值原样保留，用独立ID区分，不替原文补号或猜值。
- 目录用于导航，正文作为条款内容的直接依据。

## 4. 分类：判断义务、属性和语境，不用关键词代替语义

当前分类与验证关联统一使用[规则V1](分类与验证关联规则V1.md)。以下为案例经验，不新增类别。

### 已观察到的反例

- 标题含“质量”，正文可能是在规定签署文件、提交产物、接受审核与整改，属于过程要求，不能统一归入产品约束。
- 标题是“产品信息”，其中配置、数量、材料等字段仍可能在报价/供货语境中形成约束，不能一律降为背景。
- 只引用标准不意味着必为非需求，也不意味着必为约束类：要区分书目指针、设计约束和引用定义的性能属性。
- 没有“应/必须”的表格行，可能继承上层规范性要求；含这些词的引文或例子也不必然是独立需求。

### 判断问题

1. 谁需要满足什么能力、属性、约束、责任或交付物？
2. 要求的效力和适用范围由哪段原文或哪个表头建立？
3. 如果删除这段信息，会丢失可评估的义务或范围吗？
4. 这是产品特性、开发/交付过程，还是纯说明、定义、示例或引用？

这些问题是检查方法，不是新的硬编码分类器。原文角色与实际上下文仍需Agent判断。

## 5. 单一化：拆独立义务，保留必要条件

### 建议尺度

- 不同责任主体、独立交付物、不同验证目标或新增触发义务，通常值得分开。
- 同一属性在多个采样点/工况下的参数组，不天然变成多条独立要求。
- 同一次试验可以检验不同属性；“在同一次试验后”不是把所有验收目标合并的理由。
- 试验方法、温度、电压、次数、前后状态等是验收条件。没有独立过程义务时，不单独制造只有条件没有目标的子项。
- “或”“可以”“例如”“暂定”“仅针对”等词的逻辑必须保留；不可改成同时必需、唯一方案或已经冻结。
- 总括条款与其具体业务行要明确覆盖关系；既不能丢掉共同约束，也不能重复计算同一义务。

### 每条原文的处置应该明确

| 处置 | 含义 |
|---|---|
| 保留单一单元 | 已给出保留理由，作为一个工程核对单元继续使用 |
| 显式派生 | 产生独立子项，仍保留原文父项、共同条件和证据 |
| 共享适用约束 | 原文约束被明确绑定到具体子记录，不额外复制成重复叶需求 |
| 待澄清/补证据 | 要求或引用入口保留，但不能用缺失信息生成完整工程参数 |

“未生成派生项”本身不能证明“无需拆分”。代理必须给出可核对的处置，不能只留下数量。

## 6. 表格与图像是语义证据

- 选总表看完整逻辑表；选业务记录看适用表头、真实合并值、当前行组、共享注释及图片。
- 空白、短横线和合并单元格不同，不使用“取邻行非空值”作为统一补齐策略。
- 表号/图号可能重复或错误，定位应绑定文件、页和实际区域。
- 字符提取可能与可见字形不同。必须保留原生文字和原页，明确转写疑点。
- 页面联系图适合找布局风险；箭头、图中小字、复杂合并表头应升级到完整页面或原始分辨率复核。
- 首轮曾发生状态箭头方向误读，后通过原始图像纠正。这是Agent错误，不能转嫁给客户原文。
- 图级证据只能标为图级；未建立逐箭头/逐词映射时，不宣传该精度。

## 7. 源文问题与系统错误要分开处理

| 问题来源 | 示例类型 | 正确动作 |
|---|---|---|
| 源文档 | 参数待定、引用版本不一致、疑似模板残留 | 保留原文，列影响和澄清问题，必要时请求原作者 |
| 输入缺失 | 只有附件图标，没有附件本体 | 标记缺口，检查可读同伴内容，不补猜附件内容 |
| 捕获/转写 | 原生字符与字形不符 | 保留两层证据，明确转写修订而非覆盖原文件 |
| Agent判断 | 读反箭头、分类过粗、遗漏独立义务 | 回源修订判断，保留版本和针对性回归 |
| 结果组装 | 续行、条件、图示关联错位 | 修来源关系和组装逻辑，检查未受影响项 |
| 前端 | 数据存在但丢表注、残缺视图、反馈错目标 | 修展示/交互，不用重跑模型掩盖界面问题 |

疑点数量不是错误率。Agent提出的疑点自身也需要验证；TBD不应被自动写成确定数值。

## 8. 前端是核对与控制面

首轮实际修复包括：单行业务记录渲染失败、解释挤占原文首屏、草稿可能被确认/撤销清除、
并发后正文未同步刷新、派生问题未聚合到关注筛选、表头可访问关联不足。

据此保留以下准则：

- 优先让工程师读到完整原文与适用条件，分析理由和问题仍须容易到达。
- 内容未完整呈现时不能确认；定位高亮不等于内容已核准。
- 表格单元格内的图像/小表必须由`visualRefs`在对应单元格原位呈现并可回跳；坐标无效时显示证据缺口，不能只在整页预览里暗示已保留。
- 文内页码只能读取来源工件的显式`printedLabel`；不同文档前置页数不同，不能用PDF页号减固定偏移推算。
- 页图地址只能读取来源工件的`pages[].renderPath`并通过服务白名单校验；两位/三位固定补零都会在另一种文档上失效。
- 代理建议、Agent初稿、人工修订与最终接受必须可辨。
- 确认父项不自动确认子项；反馈绑定来源、对象和结果版本。
- 保存成功、撤销、冲突、未保存草稿、旧版本拒写都需要真实行为验证。
- 不能将模拟QA写入正式人工核对目录。未提交草稿的恢复能力必须明确界限。
- 单条核对清楚后还要验证连续作业：下一待核对项、异常队列、剩余数、快捷键和完成态决定长文档能否真正验收。

## 9. 一轮 Loop Engineering 的可审计做法

1. **固定输入与基准**：保存来源身份、旧工件、实际反馈和本轮授权。
2. **选择有意义的缺口**：明确业务标准和检查范围，不以数量增加为优化目标。
3. **给出代理判断**：逐项说明保持、调整、继续拆分或暂缺证据，记录简短依据与范围。
4. **落实修订**：保留原文，生成新版分析，尽量只改变受影响对象。
5. **验证**：来源/结构、已知业务反例、实际浏览器、反馈与版本隔离分别检查。
6. **提交对比报告**：前后变化、实际证据、未解决输入、代理建议与用户最终评判分开。

长驻核对服务可能在启动时固定工件。磁盘产生新revision后，页面刷新不等于进程已换版；
交付前应同时核对磁盘、服务API和页面显示的revision，必要时重启服务，再做最终页面检查。

一次Loop可以修订单个案例，但不能凭此宣称新会话、新文档或不同模型已稳定复现。

## 10. 后续沉淀边界

- 可沉淀：判断问题、已验证反例、证据/版本工具、结果关系和检查方式。
- 不可冒充通用能力：案例编号、固定页数、目标数量、手写答案及未声明的当前对话背景。
- 客户正文、完整案例结果及图像不进入分发包；合法可分发的合成反例用于公开测试。
- 运行、阅读、语义判断、组装和界面验证应分段记录真实耗时；研发总耗时不是稳态单文档处理时长。
- 本文是阶段性经验，跨文档适用性仍需验证；最终业务裁决保留给产品负责人。

## 11. 本轮经验的证据范围

- 固定基准含423条原文记录、471条派生草稿；代理候选未新增、删除或改写原文记录，既有派生逐项保持。
- 首版134条未展开原文全部获得显式处置：77条保留单一单元、35条拆分、5条共享范围、
  16条保留缺口、1条提取独立义务并保留共同约束。
- 扩展至16条供货业务行、5条既有派生回归样例及4条缺失附件入口，本轮共审计159条原文；
  新增122条派生候选、24处分类调整和2个澄清问题。
- 候选完整性、聚焦自动测试、实际浏览器交互和独立UI复核均已通过；人工确认保持0，
  当前状态仍是“提交产品负责人最终评判”。

这些数字只描述本轮检查范围和变化，不代表准确率，也不形成新文档的目标配额。

## 12. 全类型盘点经验与范围纠正

17类盘点覆盖PDF、DOCX、XLSX、XLSB、TIF、PPTX及多种业务角色，暴露了捕获、视觉、身份和工具问题。
但产品负责人反馈证明，把它升级为“全类型目标态”和23项决策属于范围漂移：原目标是逐份处理选定典型案例，
用户也不应面对七个入口。该盘点只保留为参考证据，不能表示典型案例完成。

- **入口与格式正交。** 用户只有客户需求文档、内部知识两个入口；PDF、DOCX、XLSX均可进入任一侧。
  同样包含参数或shall的文档也不能跨入口改变来源权威。
- **PARTIAL必须指出缺失层。** 扫描件缺可信可见文字、DOCX缺OLE关系、XLSX缺视觉格式、XLSB依赖派生、
  图片缺落格关系是不同风险，不能压成一个“解析不完整”状态。
- **稳定业务身份与适配器身份分离。** 来源、locator、内容和表格拓扑都一致时，adapter版本引起的
  SourceNode ID变化仍应触发表示迁移复核，但不应自动被认定为业务事实变化；不能靠重签oracle掩盖。
- **视觉不是OCR的同义词。** 空白页、勾选、手写批注、旋转扫描、真实表格布局、图片落格和打印公式错误
  都需要像素证据；原生结构与可见像素互补，冲突时保留两侧和问题。
- **双语与手写属于独立来源面。** 双语等价时只形成一个逻辑对象；不一致时应用权威语言规则并提示人工。
  手写在确认前是审查意见，不覆盖印刷正文或结构化表格。
- **验证规范需要独立产品对象。** 测试条件、方法、认证与PASS/FAIL可以形成TestCase及覆盖关系，
  但入口不是客户需求源时不能反向制造原始需求。
- **工具错误不能伪装成文档失败。** 相对输出目录、renderer默认写回源目录、读取不存在的状态字段都曾产生
  误导结果；通过绝对私有输出、显式output directory、真实状态字段和源目录未变检查修复。
- **数量只描述范围。** 17类、6格式、7路线、54 PASS / 61 FAIL / 2 GAP和23个开放问题都不是准确率。
  父项、派生项、知识事实、测试案例与下游决定也不能相加成一个“需求总数”。

当前目标集合恢复为主动减振器PDS、F06、E01、QC/T、PEF，并按用户要求加入QJLY。五份fresh隔离任务与
F06代理loop均已形成候选。统一前端合同是：原文父项保留，1:N派生要求直接在左树父项下生长；选择子项时
优先呈现当前要求、父项原文、共同条件和来源。全类型盘点不再拥有开发顺序。

## 13. 六份案例并行批次经验

五份fresh候选合计291页、1,612个原文条目、629条派生、157张逻辑表和45个问题；各自机器完整性通过，
但产品负责人有效反馈均为0。完整结果、逐份判断与弯路见[六份典型案例阶段审计与复盘](六份典型案例阶段审计与复盘.md)。

- 扫描件耗时主要在高分辨率页图、双OCR与逐页纠错；原生规整文档的主要耗时转向语义边界和冲突保留。
- 复杂表最容易错在逻辑身份、跨页共享条件、旋转坐标和合并值，不是普通文字识别。
- 没有情态词的试验目的/方法仍可能是要求；项目/流程义务是否进入需求集合必须由业务范围决定。
- 并行worktree适合独立案例探索，却会让页码、空白页、需求范围、语义摘要和证据展示补丁产生版本分叉。
  后续应冻结最小工件能力字段，由单一集成任务吸收前端增量，而不是继续复制整套页面。
- 每份交付必须统一包含入口报告、验证回执、工作记录、工件指纹、问题清单、Owner/QA状态和清理状态。
- 私有工件若只留在临时worktree，任务“完成”仍有持久性风险；清理worktree前迁入稳定受保护目录，但不进入Git。

## 主应用筛选与派生核对经验（2026-09-06）

继续沿用本V1的主分类，另以受控主题标签服务横向筛选。本轮使用法规、标准依据、试验验证、物流包装四个主题；不按每条文字临时创造新类别，也不把所有标准都当法规。

- UI用一个层级类别选择器选择产品/系统（全部）、功能、质量、约束、项目或过程，再与主题标签组合；不同维度取交集。
- 同一主题可以跨主类：报价费用/时点属于项目；运输、返空、审批属于过程；具体包装设计限制属于产品/系统约束。物流包装因此是主题，不是新的主类。
