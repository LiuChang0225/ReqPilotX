# ReqPilotX 作为 Pair 应用插件：原生 UI 接入评估

日期：2026-09-14。本文保留初始架构评估；共享只读入口、宿主适配合同、CSS作用域及React18兼容首增量已实施，最新证据见[实施记录](Pair只读工作面板与正文预览实施20260914.md)。实际Pair注册与完整会话接入尚未验收。

## 结论

建议在 Pair 的业务主面板中挂载 ReqPilotX 可复用工作区，保留项目、来源阅读、提取台账、分析、知识依据和版本交付等完整业务能力。Pair 提供全局导航、Agent运行与会话，ReqPilotX提供业务数据、原文与派生关系、版本和交付规则。主要工作是拆开宿主依赖，不需要重写台账／原文／表格组件。

不要直接挂载现有`App`或`main.tsx`：它们创建独立React根、控制全局路由与主题，并带有完整应用外壳。推荐新增Pair专用入口和宿主适配层，独立Web入口继续使用同一业务组件。PDF查看器可在首个技术切片中保留独立渲染边界，这不等于把整个应用放进iframe。

Pair侧依据来自整体架构任务`01a09eea-538e-7b50-a492-9a2bf00724a5`的源码核对：`sidebar.panellist`、`main` keyed slot和`ctx.layout.selectPanel(id)`可注册／打开业务面板；非conversation主面板不自动绑定Session；`dsh.client`／`./client`支持前端插件，React由宿主共享，当前Pair为React18。本UI任务只检查ReqPilotX仓库，未独立核验Pair代码或修改其布局。

## 共源约束

本评估遵循[共用能力与DSH应用插件的同步约定](跨宿主共源与DSH插件同步约定.md)和[应用插件主计划](Pair首个应用插件架构与实施计划.md)。可移植能力包是分发形态，Agent原生设计是共同执行设计，DSH应用插件是宿主包装；不由它们分别维护业务workflow。

UI的目标是一份业务组件、控制器及状态合同，Standalone入口与DSH Client两种挂载。本文“Pair专用入口”仅指薄挂载入口和HostAdapter：导航、传输、主题、容器、Portal、文件与Session能力可不同，分类、来源／派生、反馈、版本和交付逻辑仍调用共用实现。DSH官方支持的npm／Cordis bundle负责包装和服务注入，不复制另一份可独立编辑的业务UI。

React18／19对应构建可以生成不同宿主产物，但业务源代码只维护一份；适配包声明共同能力版本、UI数据合同及宿主兼容范围。业务DTO由共同合同生成／校验，UI与Agent反馈经同一业务写入口提交来源、对象和预期版本。后续检查需对照两个挂载入口的业务行为，不以Pair看起来相似或安装成功代替共源完成。

## 需要注入的宿主能力

### 1. 导航与工作区状态

`shared/navigation.tsx`目前直接读`window.location`、写`history.pushState`并使用单一全局navigationGuard；`useWorkspaceRoute`还会自动规范化`/workspace`地址。只给WorkspacePage传一个初始项目ID不够，部分业务模块自行使用该路由hook。

保留`parseWorkspaceRoute`／`applyWorkspaceRoutePatch`等纯函数，增加每个面板实例独立的navigation store，由宿主维护面板地址／恢复信息；独立Web适配才写浏览器历史。Pair面板内切模块不应跳到宿主根路径。关闭／重新打开面板可以恢复当前工作、查看版、对象和未提交草稿，卸载时解除订阅，不能终止Pair会话。

### 2. API、上传、流与文件地址

当前并非所有I/O都经过一个客户端：

- `shared/api/client.ts`用相对路径fetch及same-origin凭据。
- `shared/api/uploadTransport.ts`用独立XHR，具有上传进度／中止行为。
- `SourceItemAgentLoop`创建原生EventSource；`SourceItemReasoning`及旧Matrix导出有直接fetch。
- 图片裁剪、知识原件、下载链接、PDF iframe使用直接URL；PDF还加载Vite生成的worker资产。
- `NativeStructureReferenceDock`等PDF消息收发校验当前window.origin和实际iframe窗口。

因此应注入实例级services／transport与URL解析器，覆盖JSON、上传进度、中止、流订阅、二进制下载、原件／裁剪地址、PDF页面与worker资产。优先由Pair插件的服务桥／同源代理提供业务服务地址；具体代理能力需宿主侧确认。仅修改一个apiBase或全局覆盖fetch会遗漏这些入口，也难以支持多个面板实例。

若PDF首期仍来自ReqPilotX服务的独立页面，消息目标origin取解析后的实际viewer origin，继续同时校验iframe窗口与消息类型，不把校验改成任意来源。若改成原生PDF组件，则以props／回调替代窗口消息。

### 3. 样式、主题与容器

现有`styles/index.css`包含`:root`、`html`、`body`、通用button／input／table类和`spin`／`pulse`等全局动画；PreferencesProvider直接修改html的语言与主题。`workbench.css`与部分组件采用100dvh、window.innerWidth和fixed定位；独立Agent面板portal到document.body。这些行为必须适配面板范围。

建议首选独立插件样式入口：全部选择器限制在ReqPilotX根容器，重置和主题变量局部化，全局动画名称加插件前缀；Pair主题转换为根容器变量，不修改宿主html。保留业务内颜色与表格密度，后续再映射宿主设计token。

面板尺寸使用容器测量／container query或ResizeObserver，布局为`height:100%; min-height:0`，不能以整个窗口判断三栏和协作面板。对话框／菜单有本面板portal目标，快捷键仅在面板活动和焦点范围内生效，释放Pair快捷键；拖拽不持久改变宿主body样式。

Shadow DOM可在宿主全局样式冲突难以消除时评估，但不是无成本的默认捷径：当前activeElement、文档选区、菜单、PDF与键盘回焦均需适配。是否需要它应通过Pair实际挂载验证决定。

### 4. React共享运行时

ReqPilotX声明React／ReactDOM19.2.8与React19类型；Pair当前为React18。对运行源码的静态检索未发现`useActionState`、`useOptimistic`、`useEffectEvent`、React `use()`或自定义组件ref-as-prop等明显19专属用法；当前使用的useId／useSyncExternalStore／useDeferredValue均属于既有18能力。本地lucide-react1.27.0的peerDependencies明确包含React18。

这只支持“可以尝试低成本兼容”的判断，不能宣称已经兼容。建议插件入口以Pair实际React18版本及类型独立编译，构建externalize React、ReactDOM和jsx-runtime／jsx-dev-runtime并核对宿主解析。共享源组件可由Web19入口和Pair18入口分别构建，先不全仓降级，也不要求Pair先升级。验收必须证明只有宿主React实例，且没有React19编译产物／运行时混入；需实际挂载验证hooks、ref、dialog、portal、PDF与卸载重挂。本次未安装依赖、改lockfile或进行React18构建。

## 工作台与 Pair 会话的关系

Pair Session不等于ReqPilotX工作，也不等于来源文档。一个来源已经允许多个独立工作，每个工作又有多个不可变成果版本。不能用当前聚焦会话、文件名、最新更新时间或某个latest指针隐式决定业务工作。

建议持久化可查询的关联：Pair宿主实例／Session引用 ↔ ReqPilotX的project、document、source_sha256、work_ref。成果事件另携带result_revision／stage／artifact引用；当前查看版和当前运行head分别保存。会话新建、分叉、改绑和一文多工作需有明确动作；工作区选中行只是局部阅读状态。

最小双向交互：

1. 项目／来源选择后，用户发起业务任务时，建立Pair会话与新工作关联；已有成果从准确work＋revision打开。
2. 选中条款不自动向对话发消息。点击“在会话中讨论此条”时才准备结构化上下文：来源、查看版、结构／原文项／Snn、页面或引用范围，正文按需读取。
3. “Agent协作”打开已关联Pair会话。若当前main业务槽与conversation互斥，第一版提供往返及状态恢复；同时并排需要Pair额外布局能力，不能仅凭selectPanel承诺已有。
4. Pair工具执行保存后，用类型化成果／回执通知插件重新读取对应版本。新成果可提示打开，但不抢走用户正在查看的历史版，不从终稿文字改业务状态。
5. Pair呈现模型运行、流式输出和工具活动；插件呈现业务阶段成果、来源提示、需重评范围、反馈回执与交付状态。业务面不再复制一份通用运行轨迹或“thinking”文本。
6. 反馈保存、消息发送、运行steer／interrupt／resume按真实capability分别命名和回执。“已保存意见”不能自动变成“Agent正在修订”；没有控制能力时仍能阅读和准备草稿。
7. 仅实际需要业务决定时展示对应处置卡。结构确认保持用户可选，正式工程响应／交付锁定绑定准确快照；不能把Pair工具审批与业务接受混为一件事。

建议bridge接口覆盖navigation、services、presentation、session-link和events五组能力，接口名称属于设计建议，并非声称Pair现有这些API。会话创建／绑定、面板恢复、多面板实例、流式生命周期、文件访问和运行控制的准确宿主API，由整体架构任务继续核实。

## 实施顺序与验收边界

| 顺序 | 最小可检查结果 | 无模型调用的验收 |
|---|---|---|
| 第一切片：原生业务面板 | Pair侧栏一个ReqPilotX入口，显示准确work／revision的既有台账、结构、完整表图与原件 | React18构建和真实Pair挂载；没有双侧栏／双React／全局主题污染；刷新重开保留查看版；源数据和Excel不变 |
| 第二切片：完整业务导航与服务桥 | 项目／上传／阅读原件／知识依据／分析视图／交付都通过同一工作区与宿主适配，不另造业务模型 | 既有合成项目验证上传进度与失败恢复、下载／原件hash、PDF定位、主题、窄面板、键盘／dialog；Pair会话和工作隔离 |
| 第三切片：会话协同 | Pair负责唯一运行与会话，ReqPilotX保存业务意图、成果和回执；阅读问答侧亦完成拆分 | 以确定性事件／回执模拟增量成果、失败、重连、历史查看和重挂，不用付费提取来证明UI接线正确 |

以上是技术切片，不把第一切片的只读面板宣称为整个应用插件已交付。真实模型协作和业务语义验证仅在整体计划明确需要时另行进行；当前客户成果、已评测工件、Pair布局及共享服务保持原状。
