# ReqPilotX 开发计划：面向公司员工试用

更新：2026-10-16。首批员工入口已由用户确定为现有 ECS 方案的私有 Web；Pair 和 Windows 保留已有能力及后续验收范围。

2026-09-23原计划：本文件是唯一产品实施顺序。当前目标由“逐个方法缺口修补”提升为“形成可安装、可自主执行、可审阅纠错、可恢复、可持续维护的员工试用版本”。专项审计保留事实和详细用例，不再以其中的“最小切片”“只改几步”限制本计划的工作范围。

本计划依据本轮 WebCodex 对当前工作区的实际读取、代码核对和聚焦测试制定。下面的实施任务是后续开发要求，不是已实现或已通过的声明。

## 1. 交付目标与首批产品承诺

工程师从公司批准的入口进入，创建或选择项目、上传客户 PDF、说明任务目标；Agent 自主调查、整理结构和原文条目、判断分类与适用关系、自查并局部修正；成果逐步出现在同一个工作台。工程师可以回到原件、提出反馈、查看修订、保存人工响应，导出所看版本的完整 Matrix/Excel。关闭页面、请求失败或执行中断后，已有工作仍能找回并继续。

首批试用聚焦 **SOR 审阅、报价与技术澄清中的来源整理和人工响应**，不是 PDF 转文字演示，也不承诺无依据的自动符合性判断。没有内部产品依据时，持久保存“未执行：未提供内部依据”，但定义、条件、例外和验证目标等来源关系仍须整理，工程师仍能保存人工响应。已提供有效依据的能力按实际可用范围接入，不能把完整 RAG/知识图谱建设变成这条主线的前置。

默认自主形成可审阅草稿，不要求逐条人工审批；只有用户明确要求先确认结构时才等待。正式工程师接受及对外承诺与 Agent 完成分开。客户原文、稳定身份、既有版本、有效人工意见、内部编号和原文语言不因整理被改写或覆盖。

首批覆盖范围围绕已授权、代表性的原生/扫描/矢量/混合 PDF 建立实际证据。不能通过排除已经暴露问题的典型 BOM、里程碑、跨页试验或表图来制造“全通过”；也不要求先证明所有 PDF/Office 的所有版式都完美。暂不支持的输入、真实原件歧义和产品处理缺陷分别说明。

现行产品以 Pair 承载 Agent 会话和应用入口，ReqPilotX 维护同源业务核心、服务、工作台及技能；独立 Web 继续复用这些能力。公司实际发布入口、受控模型服务及部署拓扑必须与既有 IT 方向接续，不把个人开发机的 Pair/Codex/Qwen 运行成功等同于公司环境可用，也不因此重写一套业务产品。

## 3. 并行推进的五条工作线

五条线是责任划分，不是需要新建的管理系统。由当前主 Codex 任务承担集成责任，接续实际仍在工作的协作任务；历史文档写过“由 Pair/UI 会话负责”不等于该会话现在仍在推进。可按文件与接口边界分工，不让多人同时覆盖同一共享文件。完成一个修复后继续推进下一项可执行工作，不以“最小改动已完成”结束整个试用目标。

### A. 来源与业务结果可信：修合同，同时修实际使用

**维护范围：** `packages/engine/src/reqpilotx`、`plugins/reqpilot/scripts`，以及对应服务读写投影。核心入口包括 `source_requirement_baseline.py`、`source_item_visual.py`、`task_service.py`、task 读写/编制合同。

贯通一个来源单元的正文、表格、关联图片、真实祖先、原编号、条件和原文范围；直接组成归属与共享引用保持区别。优先完成已证实的正文＋BOM 缺口，但最终实现应解决本轮暴露的同类合同冲突，而不是对示例文字、固定行数或固定条目数打补丁。Agent 决定归属和边界，程序绑定来源、维护稳定身份并校验覆盖。

覆盖首次编制、跨页续接、精确范围、局部修订、失效关系、读回、UI 和 Excel。允许为一致性调整多层代码或做必要的职责重构；不能只删互斥校验、静默吞 scope、把共享引用当直接拥有、把正文伪装成标题，或为了减数把需求降类。旧工件不重新计算身份。

同步解决会影响完整任务的分析策略持久化、未决 finding 处置和交付回包。已有 review 的策略更新不能靠重新建任务；修订成功不自动关闭仍未解决的语义问题；同版已登记导出应可复用，当前状态与历史回执中的旧下一步要区分。

对里程碑、完整试验、产品组成分类、父级共同义务及验证目标关联同时排查“错误决定”和“无法表达/漏保存”。复用通用来源引用；只有证据证明当前关系合同会丢失所需含义时才补必要表达，不预先建设泛化关系图。

**完成依据：** 正例与反例通过真实公开编制入口完整保存；遗漏、重复、错祖先、错误条件/目标关联能够被核对发现；合法局部修改后原文、归属、关系、版本与同版展示/导出保持一致。程序覆盖和源语义分别成立。

### B. 有效方法可复用：开发 Agent 发现，再让目标 Agent 复现

**维护范围：** `agent-assets/current/plugin-skills`、既有 reference/示例资产、`evals/agent_evals` 的方法微测。按现有资产机制同步宿主投影，不在 Pair、Web、插件各写一套 prompt。

围绕实际失败，亲自完成“证据取得→语义决定→公开工具表达→保存/修订→读回/交付”，记录有效动作和无效尝试。可自由阅读全文、跨页观察、裁切、调用现有 OCR 或视觉转录；不恢复按算法候选强制分组的限制，不为自由调查设固定页白名单，也不整本无差别 OCR。

收敛初批方法族：编号与纯标题/父正文；里程碑与参数；完整 BOM 与独立配置；完整试验与不同试验；定义/条件/例外及目标引用；支持图/独立图与扫描表。普通稳定情况给一个完整示范，易混边界给能改变判断的对照。不是先把全部材料写完才运行，也不把第一张方法卡当整个方法工作的完成。

清理 T05 等含混或互相冲突的表述。每份示范使用当前 schema、实际保存输出及当前宿主可读的原例；不能用 CLI 可运行推断 MCP 必然可达。包含正常首次编制、有价值的局部纠错和正确结果无需改动；维护者写方法资产，不要求运行 Agent 每条填写额外表格。

处理尚存读取限额、literal query、schema 导航及反复搬运身份等机械负担时，先沿实际调用定位。已有 `max_chars` 截断不等于 `limit>100` 已容错。确定性引用/版本/错误恢复交给程序；歧义和语义选择不能静默自动“纠正”。

**完成依据：** 开发者成功操作、示范资产可达、新 Agent 实际选用及未见过的反例做对分别记录。换版式不换含义时保持边界，改变独立事项时边界随之改变；新原件的坐标重新绑定。不能拿读过示范、复制答案或模型复述规则作为理解证明。

### C. 员工操作闭环：把已有工作台变成真正可工作的界面

**维护范围：** `integrations/pair/host`、`integrations/pair/client`、`packages/workbench-ui`、`apps/server` 的共用 API；Web 外壳使用同一合同。

完成从上传、委托、阶段成果、原文定位，到反馈、局部修订、人工响应、版本对比、导出的完整路径。员工不需要命令行、手拼 task ID/内部 URL、自行复制结果或依赖开发者代写工件。能在原文/表格审阅之间切换，保持选中对象、当前版本和意见草稿。

从当前只读 Panel/Client 演进为按真实能力提供操作的共享工作面。贯通自然语言反馈的已保存/待取回/已修订/仍未决状态，以及人工响应与其依据、作者和版本。正式工程师意见必须独立于 Agent 自评和普通聊天；不能用聊天“收到”代替持久保存。权限与版本检查在服务端执行，不能只放开代理写白名单。

接入任务停止/取消与业务恢复：取消针对实际绑定会话/任务，说明已保存成果和未完成范围；不承诺已提交写入会自动回滚。刷新、服务端点变化、宿主重启、重试或重连后能找到原工作，不能另建重复任务或换到别人的版本。复用现有 receipt、journal、版本冲突和 task recovery，而不是重建调度平台。

沿用真实进度轮询和已保存成果更新，重点呈现“正在处理什么、已有多少可审阅结果、当前是否等待/失败、下一步能做什么”。模型调用数可在诊断层查看，不作为员工主进度。push 仅在轮询的实际问题需要时建设，不以协议选型延误试用。

整理日常入口，统一未开始/部分完成/失败但已有成果/草稿已形成/人工已接受的语义。旧客户版本、深链接及历史意见保留；新员工不再被引导进入候选评测壳、旧流程或需要粘贴内部链接的开发探针。

**完成依据：** 在真实目标浏览器/宿主用新任务完成整条旅程；一次反馈能生成正确局部修订，一次人工响应能进入同版导出；取消、刷新、重连和历史查看不丢工作、不串任务、不重复执行。仅 HTTP 200、组件测试或返回 URL 不算界面验收。

### D. 公司运行与发行：与功能开发同时收尾

**维护范围：** `integrations/pair`、`apps/server`、现有部署/构建脚本、`docs/deployment`；身份、模型与基础设施依赖接续公司已有 IT 安排。

先把“员工从哪里进入、服务与 Agent 在哪里运行、数据在哪里保存、允许调用哪个模型服务”落实为一份可执行的试用配置。当前 Pair 本地托管是已经存在的路径，不是对公司多员工部署的自动授权；此前 Web/云端/受控 Azure 服务的 IT 方向也不是已经部署完成的事实。优先复用批准的身份与运行服务，避免同时维护多个都无法交付的首发路线。

开发评测的 Luna Max/Qwen High 与员工使用的批准模型服务分开。代码中已有 Azure 配置/旧适配器，不证明当前 Agent 工具、视觉、会话和凭据刷新已经贯通。核对实际宿主的受控模型路径；需新增配置或迁移时沿宿主/模型适配层实施，不复制业务核心、不偷偷复用个人登录或把旧评测成绩外推为企业模型质量。

交付可复现、配套的 engine/server wheel、冻结能力包、共享 UI/Web、Pair adapter 及依赖清单，按现有发行结构构建；员工操作不依赖开发 checkout 或手工调试环境。缺依赖时给可操作诊断。由安装器或部署过程处理依赖，运行中不静默下载/切换能力包。首批实际使用的设备、系统和浏览器必须验证，不能拿 Mac 开发机通过代替公司目标机器。

若采用跨机器/集中 Web 访问，修正 PDF viewer、资源下载和回调中的 loopback 假设，明确浏览器、业务服务和 Agent 的网络边界；若批准的是本机托管试点，就按本机数据边界验收，不宣传为共享云产品。公司身份、项目/文档/任务/下载权限及操作归属沿全链验证；Host/Origin、存储 applicationId 和任务身份不能代替用户授权。

把上传限额、文件类型/读取失败、临时空间、并发任务、受控出网、凭据刷新、日志脱敏、运行诊断、数据库与对象备份恢复纳入试用准备。默认不记录客户正文到普通诊断日志，不把账号凭据放在 CLI 参数或发行物。长任务可观察、可停止；预算/并发使用可配置策略，不降低用户指定推理档位来伪装优化。

**完成依据：** 同一候选在干净目标环境完成安装/启动、批准模型连接、源文件/图像读取、正常任务及恢复；完成至少一次与该数据拓扑匹配的备份恢复演练。实际身份/权限/数据路径及支持方式清楚。云资源开通、账号批准等外部依赖由责任人推进，不能阻止其余可实现工作继续，也不能被标为已完成。

### E. 集成验收与试用运营：验证的是发布产品，不只是某条分支

**维护范围：** `evals/agent_evals`、现有私有案例、前后端/插件/Pair 测试和 `.github/workflows`，以及目标环境的发行验证记录。

沿用 L0–L3 和既有评分体系。先证明公开工具可表达，随后测自然入口与阶段行为，最后用固定候选和代表性原件做自主整链。方法改动跑受影响用例；跨层合同和发行改动扩大到相关集成范围；发布候选不能拼接不同包、不同宿主或不同源码时点的通过结果。

首批验收必须包含一份代表性真实原件的自然冷启动整链，覆盖此前主要缺口；已有原件回归与真正未用于调参的资料分别标记。必要时用多份资料补足关键风险，不用任意固定文档数冒充泛化证据。缺合法留出时保持明确，不把用过的案例改名留出。

程序完整性、来源语义、实际 UI 行为、人工响应/版本、恢复和模型成本分别报告。来源语义检查关注遗漏/重复、边界、编号/祖先、条件例外、图表和关联，允许来源支持的合理替代结果；评核要能拒绝已知错误，不以固定 SRC/REQ 数或编译器自洽作为答案。

当前开发新运行沿用 Codex Luna Max 与 Pair Qwen3.8-max-0902 High；本次 ChatGPT 评审不是新增生产者/裁判配置。按实际授权开展必要运行，工具已知不可能完成时不长跑，组合改动不伪称纯 skill 因果。公司试用模型如不同，须在其获准配置上取得对应证据，不能自动沿用开发模型成绩。

记录首个可审阅成果、自然完成时长、有效/失败工具行为、局部纠错成本、员工回源成功与完成任务所需操作。预算和可接受等待按目标文档及实测制定，不预填虚假 SLA，也不只优化 token/调用数。发布前需要真实主路径和故障恢复证据，不需额外付费模型裁判评整本。

**完成依据：** 可分发的同一候选、绑定来源和版本的验收结果、实际员工入口验证、明确缺口清单和使用/恢复说明齐备。再安排首批工程师以自己的业务任务试用，收集真实问题而非演示者代操作；问题沿现有反馈/专项/评测入口闭合，不另建追踪平台。

## 4. 实施节奏：并行推进，按产品结果汇合

| 推进段 | 应当连续完成的工作 | 汇合结果 |
|---|---|---|
| 立即接续 | 对账现有未提交增量和实际协作责任；A 修混合归属及状态，B 同步方法和反例，C 接反馈/人工响应与任务控制，D 落实试用环境及发行路径，E 准备用例和真实界面验收 | 从“审计有结论”进入实际实现，各线都有可消费的接口/工件，不等待全部语义优化完成才动 UI/部署 |
| 集成候选 | 将共用核心、技能、宿主、工作台和环境配置合成一个兼容候选；持续做相关程序/接口检查；完成首条完整员工操作链 | 员工能够完成业务动作，不需开发者拼装；不再只按模块各自通过报告 |
| 质量与恢复收敛 | 固定兼容候选做有针对性的目标 Agent/真实原件验证；缺陷回到对应层修复；检查取消/恢复、关系修订、人工响应与同版导出 | 达到下节的试用准入条件，仍未解决的真实输入问题与支持范围清楚 |
| 员工试用与扩展 | 发布至获准试用环境；用真实工程任务收集反馈、修复回归、更新方法和版本；根据实际需求扩文档类型和依据分析 | 可持续使用与维护，而非一轮演示后再次重建 |

A 的可表达性影响相应 B/E 方法验证，但不阻塞 C/D 的实现和合成接口测试。C/D 的真正员工入口不能永远后置到“所有 skill 已稳定”。E 是持续质量反馈，不是最后单独盖章的部门。

进入最终候选时完成可追溯的源码集成与产物构建。运行中的任务保持原固定包；修复进入新候选/新运行，不中途替换旧包后重标成绩。版本发布、仓库推送与环境部署按现有实际授权执行，不能用“计划已更新”冒充已经发布。

## 5. 员工试用准入：不追求虚假的完美，也不掩盖阻塞

| 条件 | 试用前必须具备的结果 |
|---|---|
| 入口可用 | 工程师在批准环境中可独立上传、委托、查看、回源、反馈/响应和导出，不需要开发者代操作 |
| 来源可信 | 目标范围的主要已知系统性遗漏、重复、错误归属/条件和混合表达问题已关闭；支持范围有真实验收证据。未读/未处理范围明确可见，不能显示为完整通过 |
| 人工可纠错 | 反馈进入正确任务和版本；局部修订可核对，正确内容保留；人工响应不被后续 Agent 修改静默覆盖 |
| 运行可控制 | 能停止实际任务，刷新/重连/重启后恢复已有工作；重复请求不制造重复业务结果；当前执行状态可解释 |
| 数据与版本正确 | 无跨用户/项目/任务越权和错绑；原文/表图/关系/有效响应的工作台与 Excel 同版；历史成果可读且不被覆盖 |
| 环境可交付 | 目标设备/部署实际运行，批准模型和身份路径完成验证，配套版本明确；有可用诊断、备份恢复和失败处理说明 |
| 试用有负责人 | 首批实际使用者、支持渠道、缺陷处理和版本升级方式明确；开发者不能成为每份文档必需的手工操作员 |

真实原件歧义、客户漏附件或尚未定义的参数，可作为带定位的待澄清事项进入草稿；这不等于产品必须阻断整份文档。已知处理错误、未处理范围和未经验证的来源不能以“AI 草稿”名义伪装为完整可靠结果。AI 草稿完成不授予对外承诺权。

不作为首批统一前置：所有 Office/任意复杂版式、ReqIF writer、全量知识图谱/检索平台、所有桌面系统、push 替代现有有效轮询、纯审美重排或无业务收益的框架迁移。首批员工实际需要的目标系统、来源类型和安全要求不能用这段排除。

## 6. Codex 的持续工作方式与每轮交接

主 Codex 以“员工还在哪一步无法完成工作”为持续优先级。每轮从当前源码/回执核对变化，选取阻塞结果的原因并直接推进；无新证据时不重新写一份全面审计或发明新的工作流。必要的多层修复、重构、技能调整和测试可以在同轮完整做完，不把修改行数、文件数或预设步骤数当上限。

固定责任，不固定阅读路线：Agent 保留调查和语义判断自由；程序负责确定性身份、范围、版本、保存、编制与恢复。将一次有效修正转成适当的代码/示例/回归，而不是每次要求模型“更仔细”。同类问题反复出现时检查维护源、构建投影、任务冻结包与实际宿主，不能只在源码 skill 继续加文字。

每轮在现有记录中说明：本轮哪个员工动作或来源问题已经可用；实际改了什么；在哪个源码/产物/宿主上验证；还有什么阻塞；下一轮直接继续什么。实现、程序测试、真实界面、来源语义、工程师接受分别记录。无需新增五套状态表、每日控制塔或运行 Agent 的形式化记账。

维护计划时更新本文件的顺序/当前优先事项；`active-context.md` 只保留接续证据；专项保存详细实施和反例；reference 保存可执行方法；评测记录保存实际成绩。清理活文档中“上文待实现、下文已通过”等矛盾，历史记录保留当时事实，不批量重标。
