# 原文编号水位与历史重放

2026-09-08：修复 legacy 初始基线 `source_display_high_watermark=None` 时，scope split → UNDO → 分类修订 → 后续分配复用退休 SRC/REQ 号的问题。新修订由程序恢复并持久保存历史水位，Agent 不选择号码。旧冻结工件、回执、哈希及既有业务判断不改写。

## 复现与修复

无图片的合成原PDF，初始8个SRC。旧策略第一次split分配SRC-0009/0010；UNDO退休这两号，active最大号回8，但baseline水位仍None。分类修订不复制旧scope receipt，下一次其它scope split便再次将0009/0010分给不同的`source_record_id`，旧`review-verify`仍通过。

同一原PDF、同一初始baseline经新策略复演：split后水位10；UNDO与中间分类后保留10，下一scope分配0011/0012。不会把另一个原文对象赋予已退休显示号，也不把退休号改写为新对象。已发生的旧历史只按原策略忠实重放，不用本次修复重写过去。

## 程序接口

`review-revise`拒绝调用者输入`source_identity_allocation`或`source_display_high_watermark_floor`，随后从当前绑定的旧review SHA顺序核验其真实历史prefix。程序生成`source_identity_allocation`，包含：

- 策略`REVIEW_HISTORY_HIGH_WATERMARK_V1`。
- 旧review SHA、历史prefix摘要、source SHA、previous baseline id/SHA。
- 从历史active身份、显式baseline水位及对应已验证scope receipt恢复的最高水位。
- 上下文自身摘要。

新revision-input保存该上下文。单纯自签上下文摘要不能证明历史：public verify必须从该旧review SHA再次按顺序重建全部字段并严格相等。前缀读取核对immutable review snapshot、登记文件哈希、同源baseline及真实前驱；每个transition经其原有策略重放。一次扫描向后传递已验证水位，不递归调用自身verify。历史缺失或漂移时拒绝，不以active最大号猜测。

共享scope build/compile及classification compiler新增可选keyword-only `source_display_high_watermark_floor`。默认None保持旧合同及原hash；新程序调用把真实历史floor写入已有baseline水位字段。scope receipt继续绑定真实前驱与实际输出，不搬运或重签旧proof。分类/注释中间目录不需要复制旧scope receipt；无baseline变化的注释修订保留baseline，程序上下文仍记录在revision-input，下一次分配仍扫描真实历史。

`map_tools.compile_map_transition`及`rebind_baseline_for_document_map_revision`新增可选`source_identity_allocation`，核对上下文与真实previous source/baseline的绑定。新Map投影采用该floor；Map+TEXT恢复的nested scope proof必须以该floor分配。新Map回执包含完整上下文，public review verifier以历史复演验证它；下游仍根据实际final baseline反构scope输出并比较id/hash，不能用另一个自洽hash蒙混通过。旧无上下文Map回执完全沿用原验证。无新增SRC的Map继承也允许这个已验证水位元数据升级，保持SRC/REQ、退休registry与判断不变。

历史扫描限定于当前review。若一个legacy基线从外部导入且没有显式水位，也没有该review中的历史证据，程序不能凭空推知导入前已退休的号码；此类来源缺失需明确的历史迁移，不能猜数。本轮不扩展到其它身份或全局目录扫描。
