# 分类与验证关联规则 V1

采用日期：2026-09-05。适用范围：当前汽车客户 SOR 的原文理解、需求提取与核对。
依据用户“评估当前规则，合适则先定稿并进入下一步”的授权，经当前案例与定义核对，采用本 V1。
这表示采用工作口径，不表示模型已泛化、12例/全文已验收或正式 API schema 已冻结。
本文件取代 r2 的“项目/过程统归约束”简化；开发顺序仍由[开发计划](开发计划.md)决定。

## 原文保留与 A 判断

全部原文、层级、逻辑表、表头/共享值/表注、图片及附件引用保留。A 的需求/非需求判断用于默认是否单列独立评审，
不控制来源保留、Agent可见性或上下文调用。非需求或暂不独立评审的内容仍可能是重要的规范性依据。

- 不按是否出现 shall、必须、应等词机械判断。建议、许可、适用条件、事实是内容作用，不自动决定 A。
- 混合父项保留整体与解释；当前工作判断、输入缺口和用户接受是不同状态。
- 规范性试验片段若仅支撑完整试验，可在私有核对投影中显示“关联验证规定”，不强行分配独立产品类别或派生ID。
  这是一种关联/评审处置，不是新增需求类别；其规范性、适用范围、来源与产品技术评审关系继续保留。
- 真正独立规定某执行流程的要求可以归过程要求。过程不等于非技术，不能因此把技术试验送到仅项目管理评审。

## B：有限需求树

```text
需求
├─ 产品/系统需求
│  ├─ 功能
│  ├─ 质量（含性能）
│  └─ 约束
├─ 项目要求
└─ 过程要求
```

| 类别 | 判断依据 |
|---|---|
| 产品/系统 · 功能 | 产品需要提供的行为、结果或能力；“可独立控制”可表达能力，不等于可有可无的许可 |
| 产品/系统 · 质量 | 产品的性能或质量特征及其条件；数值阈值、温度、次数、容差不因形式而成为约束 |
| 产品/系统 · 约束 | 原文确实限定设计/实现/配置等解空间；不能仅因出现方法、条件、法规或标准名称就归此类 |
| 项目要求 | 项目周期、交付物、报价事项、里程碑及其时点/触发条件 |
| 过程要求 | 组织活动、流程、职责、审批与执行规则；保留其技术或管理对象 |

包装、可靠性、静态电流、安全等保留为主题或原文章节；设备、方法、参数、判据是结构作用。
不新增并列的“试验/验证要求”大类，不建立无限主题主类，不造组合枚举。
混合父项可表达多个树节点；分类关系与可选派生不同，不为了分类拆原文。

## 需求类别与验证关联分开

完整试验的设备、样品/装配状态、导线、介质、条件、方法、方向、顺序和判据共同参与技术评审。
产品力学/电流等性能归质量；验证方法本身不统一归功能、质量或约束。
原文片段拥有独立locator，不意味着需要独立产品类别或新派生ID。

用小型、可回看的关联保存“判据→设备/对应方法”“参数→表格”“正文→引用标准”“责任/许可→适用范围”。
目标是否已读取、读取范围与缺失输入要明确；不能借关联补造未取得的标准正文。
评审方式按实际对象与内容决定：项目交付由项目组针对性核对，产品验证条件始终随技术评审出现，不机械由类别路由。

## 引用、范围与拆分

- 法规/标准是依据属性和引用关系，可支撑功能、质量、约束、项目或过程内容。技术标准不自动等于法律。
- 只有总体遵循条款时，保留总体要求与引用；没有正文不编造条文。清单可以不单列独立分析项，但不能被当作无关背景。
- 完整条款/逻辑总表优先保留，不按句、行、页机械拆分；参数与条件不能脱离所限定的目标。
- 文档结构、分类、验证关联与可选派生是不同关系。只有有业务必要且明确授权才派生；父项和双向追踪保留。
- 已接受且未受影响的内容不改写。规则采用、Agent修订、机器校验、用户逐项接受分别记录。

## 常见反例

| 不当推断 | V1处理 |
|---|---|
| 电流上限是数字，所以是约束 | 按产品能耗/电流性能判断质量，保留条件与例外 |
| 方法写了“应”，就再造一条产品约束 | 先识别是否完整试验的关联验证规定，保留规范性和技术评审关系 |
| 项目交付/审批都塞入约束 | 区分项目时点/交付与过程职责/审批 |
| 参数表或BOM每行都是独立要求 | 保留完整结构与共同语义；不按行机械造规范句 |
| 标为参考便不必让Agent读取 | A不控制可见性；引用内容仍可成为必要规范性依据 |
| 法规标题意味着所有未来法规都必须满足 | 保留原文适用范围、引用和时态；未读正文不扩张义务 |
| 允许某架构不执行试验，是产品设计约束 | 保留责任、适用性与许可关联，不冒充独立产品指标 |

## 官方依据与限制

[IREB CPRE术语表](https://cpre.ireb.org/en/downloads-and-resources/glossary)区分系统、项目、过程要求，系统需求下区分功能、质量与约束，性能归质量。
可验证性描述能否验证已实现系统满足该需求，不推出“每个可定位片段都必须拆为需求”的规则。

[NASA Product Verification](https://www.nasa.gov/reference/5-3-product-verification/)把需求基线与验证方法、设备、环境条件及程序关联；
其验证报告保留需求追踪与这些验证信息。这支持完整验证上下文的重要性，不是给ReqPilotX规定完整本体或UI枚举。

V1是当前汽车客户SOR的工作口径。业务/干系人需求管理、标准等价分析和法律咨询不扩入当前范围；内部知识是否可用须按当前项目的真实授权文件判断，源码演示不构成内部依据。
后续使用明确授权的连续来源范围核对规则，保留失败与待决项；开发用案例不算盲测、独立复现或通用提取器完成证明。

采用V1后，普通案例差异先局部修订分类、适用范围或关联；只有真实条款无法表达且影响评审时，才重新讨论主类。
