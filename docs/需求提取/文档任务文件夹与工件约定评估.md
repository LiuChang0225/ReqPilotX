## 当前建议

**直接采用实体文档任务工作区。一个项目有多份文档，每份文档有可跨运行接续的任务目录；程序维护工件位置、确切版本和动态任务简报，Agent自由阅读、编制、自查和修订。首增量不以通用数据库注册表、document family或多unit实体为前置。**

当前最小组合是“小型代码工件字典＋每任务机器索引＋现有review/plugin/native持久化适配”。保留已有编译器、原件与版本链、已实现的统一DocumentWorkSurface和协作/交付能力；补真正可执行的任务初始化、程序自动选址、前端绑定、已有/剩余范围和失败接续。

Astra复评明确纠正Sol原方案：把family和多张通用注册表放进首个增量，会把用户要的Agent工作环境改写为平台迁移；将实体目录排在新注册层之后、或仅作可选临时投影，也会削弱可发现、可恢复的目标。主任务后来决定“不先迁DB”是合理的，但“类型字典＋索引”仍须交付真实任务根和程序接续能力，不能只停留在后端文件清单。

| 当前采用 | 本轮边界 |
|---|---|
| 项目→文档→持续任务；task与run分开 | 原生复用已有task_id/workspace；portable保存本地work-id并关联真实plugin session/review，不把各owner身份混成同一ID |
| 固定工件类型、位置与读取责任 | 沿用现有同版bundle和完整证据依赖；不把所有文件清单合为同一必需集合，不让Agent手写head/hash |
| 程序生成TASK入口、动态context和index | 明确目标、正在继续的版、已保存/剩余/未知范围、待确认和实际命令参数；建议下一动作不限制全文阅读 |
| 现有owner保持权威 | PostgreSQL、object store、宿主管理的task/stage/plugin文件各承担现有职责；应用可见的插件版本不因没入新SQL表而被降级为“未注册” |
| 同版展示/导出与显式producer选择 | 复用P2外壳和已有API；增加文档下已存任务/成果的列举，不按mtime或跨任务vN选唯一胜者 |
| 原件、反馈、知识和历史保持 | 新原件字节另建绑定；多根结构现在就按模型V1表达；family/unit独立生命周期与跨SHA意见继承后续再做 |

# 文档任务文件夹与工件约定评估

更新：2026-09-12。状态：**专项评估，尚未实施。** 本文只评估“一个项目包含多个文档工作区、每个文档使用固定工件类型并映射到统一前端”的可行边界，不改变[统一工作流与工作台专项](统一工作流与工作台专项.md)及[开发计划](开发计划.md)的实施顺序，也不声明新增命令、数据库表或前端入口已经存在。

## 结论

**建议采用，但采用的是“稳定文档身份＋受控工件类型＋机器生成的工作区投影”，不是把文件夹变成新的业务数据库，也不是把 Agent 固定成逐目录执行的流水线。**

这套约定能直接解决当前的三个断点：Agent 容易在长任务中丢失有效中间成果；native、plugin、本地 review 对同一种成果各有清单但没有共同注册语义；前端只能从任务、URL 或特定 `head.json` 猜“有什么成果”。真正成立需要同时满足以下边界：

1. PostgreSQL 中的业务身份、版本关系和注册记录与 object store 中的不可变内容仍是原生应用真相源。文件夹是 Agent 可读写的私有任务区，或由注册表物化出的可携带投影。
2. 固定的是**工件类型和契约**，不是必须串行完成的步骤。Agent 可先整体阅读、跨页回查、并行处理独立范围、反复修订 Map；程序只在保存时校验身份、哈希、schema、范围和前驱关系。
3. 原件文件、逻辑文档、原件版本、文档单元、执行任务、producer、结果版本必须分开。文件名、目录名、修改时间和“v3”不能承担这些身份。
4. Agent 不手写“当前 head”“所有文件已完成”之类机械 manifest。程序负责初始化、分配 ID、原子保存、注册、CAS 更新 head 和生成工作区索引；Agent只提交业务候选与明确操作参数。
5. “已落地”“已注册”“可展示”“已验证”“已接受”是独立事实，不能从文件存在或页面能打开互相推导。

当前已有足够复用基础，无需先建一套新的存储系统：原件已有 `sor_documents + stored_objects`；提取结果已有 object-store 生命周期、staging/CAS 和回收；native working revision 与 delivery version 已有不可变版本；plugin 与 portable review 已有哈希、锁、版本前驱和幂等写入。缺口是共同身份层、工件类型注册和统一读取投影，而不是缺少更多人工目录。

## “PPT Master”参考的适用程度

“ppt master”不是唯一项目名。公开检索可以找到多个同名仓库；本文只把 [hugohe3/ppt-master](https://github.com/hugohe3/ppt-master) 当作用户所指对象的**候选参考**，没有把这一对应关系视为已确认事实，也没有安装或复制其代码。

该项目值得借鉴的部分，是把安装目录、长期工作目录和一次 active project 分开，并用程序提供 `init / import-sources / validate`，active project 下承载来源、编辑中成果、报告、备份和导出；其[入门说明](https://github.com/hugohe3/ppt-master/blob/main/docs/getting-started.md#set-up-the-installation-and-working-folders)与[项目入口](https://github.com/hugohe3/ppt-master/blob/main/AGENTS.md#core-directories)都明确了这一点。它的文档也明确说明 Quick 模式不保存可恢复的设计决策，丢失上下文后要重来；这反而说明 ReqPilotX 不能照搬“一次生成一个项目目录”的简化模型，因为需求工程必须保留来源、反馈、人工决定和版本链。

因此可借鉴“受控项目根、程序初始化、已知工件位置、统一校验”，不借用它的阶段语义、单一 deck 身份或以文件夹本身作为产品状态的做法。

## 身份模型：先解决目录无法表达的事实

建议所有目录和工件注册都显式带以下身份。括号内说明当前最接近的实现及缺口。

| 身份 | 含义 | 当前实现与缺口 |
|---|---|---|
| `project_id` | 客户项目；拥有共享知识和多个逻辑文档 | `projects.id` 已有；知识库版本与项目绑定，可直接复用 |
| `document_ref` | 人理解的稳定逻辑文档，例如“PDS” | 当前 `sor_documents.id` 是一次上传生成的 UUID；再次上传同名修订会得到新 ID，没有同一逻辑文档的版本关系 |
| `source_version_ref` | 一次不可变原件版本 | 可先复用现有 `sor_documents.id` 作为上传版本；必须与稳定 `document_ref` 分开 |
| `source_sha256` | 原件字节身份 | 已贯穿 capture、Map、baseline、任务和导出；仍应作为所有工件的硬约束，不等于逻辑文档 ID |
| `document_unit_ref` | 一个物理文件内按真实来源识别出的独立文档单元 | 产品模型已要求“独立附件可与主文档平级”，当前尚无独立注册实体；不能用页码范围或扩展名代替 |
| `work_ref` | 用户正在持续处理的工作分支 | 当前 native task、plugin session、legacy Set 各自承担一部分；需要规范化引用，不合并真实历史 |
| `producer_ref` | 产生工件的真实执行来源 | 至少有 `NATIVE_APP_SERVER`、`EXTERNAL_PLUGIN`、`PORTABLE_REVIEW`、`PROGRAM`、`USER`；不能只写“Agent” |
| `run_ref` | 一次可暂停、失败、恢复或结束的执行 | native task/job/run 已有；plugin 外部运行可能不可知；run 不是成果版本 |
| `artifact_version_ref` | 某一类型工件的不可变版本 | Map/baseline有内容身份；native working revision、plugin revision、本地 review 各自有版本，但无共同注册记录 |
| `result_ref` | 一组相互兼容、可被同屏读取和导出的工件固定集合 | plugin `version.json` 和 review `current.files` 已近似表达；应用尚无跨 producer 的统一结果引用 |

### 同文件修订

同名文件再次上传不能覆盖原目录，也不能仅凭文件名自动判定为同一文档。推荐先由用户或明确导入参数选择 `document_ref`，程序创建新的 `source_version_ref`，保存 `previous_source_version_ref` 和新 SHA。旧原件、Map、条目、反馈及交付全部保持可读；新版本是否继承条目身份、反馈或分析必须经过来源差异和重绑定程序，不能按目录复制。

相同字节 SHA 可在 object store 去重，但“同一字节被登记为两个项目文档”仍是两个业务关联；去重不能合并文档权限、目标或审阅状态。

### 一个文件含多个文档单元

一个 PDF 可能同时包含主 PDS 和独立试验大纲。它们共享一个 `source_version_ref/source_sha256`，但拥有各自稳定 `document_unit_ref`、真实来源范围和相互关系。Map 可以有多个根，但仅靠多个根无法长期表达“独立文档”“正文附录”“嵌入附件”之间的身份和版本关系；建议将文档单元作为经程序注册的来源范围实体，并让工件注册携带 `unit_scope_refs`。

不得为每个物理页建文档单元，也不得把“文档单元目录”变成强制语义切分步骤。Agent先按真实来源判断，程序校验范围、重叠和父/平级关系后注册。

### 同项目共享知识

共享知识只在项目层注册一次。每次分析工件固定其实际读取的 `knowledge_catalog_sha256 / knowledge_base_version / selected_document_ids`；文档文件夹内只物化该快照的引用或受控副本。把当前知识库全文复制到每个文档并让 Agent自行判断“哪份最新”，会产生第二真相源，也会让旧分析无法重放。

## 推荐目录树

下面是**逻辑结构**。原生应用可以按需物化到任务私有目录；object store 不需要真的以本地文件夹展示。所有 `index.json / registration.json / head.json` 均由程序生成，Agent不得直接编辑。

```text
project-{project_id}/
├─ project-index.json                         # 机器生成：项目、文档、共享知识引用
├─ knowledge/
│  ├─ registrations/                         # 项目知识登记投影，不是文档副本的真相源
│  └─ snapshots/{catalog_sha256}/            # 本次分析实际使用的冻结目录/证据引用
└─ documents/
   └─ document-{document_ref}/
      ├─ document-index.json                  # 机器生成：逻辑文档及可用原件版本
      ├─ originals/
      │  └─ source-{source_version_ref}/
      │     ├─ source-registration.json       # SHA、storage key、文件名、前一原件版本
      │     ├─ original.{ext}                 # 私有任务区中的受控副本/只读物化
      │     └─ units.json                     # 程序注册的 document_unit_ref 与来源范围
      ├─ reading/
      │  └─ source-{source_version_ref}/
      │     └─ capture-{capture_ref}/         # SourceIR、页文本、原表、原图、阅读投影
      ├─ artifacts/
      │  ├─ document-map/{artifact_version_ref}/
      │  ├─ source-ledger/{artifact_version_ref}/
      │  ├─ annotations/{artifact_version_ref}/
      │  ├─ decomposition/{artifact_version_ref}/
      │  ├─ assessments/{artifact_version_ref}/
      │  ├─ manual-decisions/{artifact_version_ref}/
      │  └─ findings/{artifact_version_ref}/  # 当前尚无通用持久化类型
      ├─ results/{result_ref}.json             # 机器生成：固定同屏/同版工件集合
      ├─ runs/{producer_ref}/{run_ref}/
      │  ├─ run.json                           # 目标、能力、真实状态、游标
      │  ├─ events.jsonl                       # 公开事件/回执；不保存隐藏思维链
      │  └─ scratch/                           # 尚未注册的候选；可清理、不可被前端当成果
      ├─ feedback/{feedback_ref}.json          # 绑定 result/Map/baseline/对象范围的不可变意见事件
      └─ deliveries/{delivery_ref}/
         ├─ delivery-registration.json        # result_ref、范围、状态、snapshot SHA
         ├─ matrix-snapshot.json
         └─ matrix.xlsx
```

这棵树不按 `01-capture → 02-map → 03-items` 编号。阅读投影可以在 Map 修订后继续补充；Map 与条目可做受影响范围的局部修订；反馈和交付也不属于语义解析步骤。固定目录只回答“这是什么”，不回答“Agent下一步必须做什么”。

| 原表投影 `TABLE_PREVIEWS` | 捕获/编译程序；当前为受 Map/baseline 校验的 JSON，**没有独立统一 schema ID** | 随 `compile-map/compile-items` 产出和校验 | 原表详情、长表视图、PDF对照 | 必须与 Map/source SHA 同版；不应单独设“最新表格”head |
| 原文账本 `SOURCE_LEDGER` | Agent决策＋共用编译器；`source-requirement-baseline-artifact/v1` | `compile-items`、`compile-images`、`review-revise` | `SourceLedgerTable`、`SourceItemLens`、统一条目台账 | 已有 predecessor、覆盖范围和 COMPLETE/PARTIAL语义；当前跨producer不可比较revision数字 |
| 校验收据 `VALIDATION_RECEIPT` | 共用编译器；`source-requirement-baseline-validation-receipt/v1`及专项收据 | 与各 `compile-* / review-*` 同步生成 | 成果就绪/限制摘要，默认不作为独立业务页 | 必须作为所校验工件的伴随证明，不能替代来源语义或人工接受 |
| 图片释读/原编号等注解 `ANNOTATIONS` | Agent观察＋程序校验；`source-item-image-annotations/v1` | `image-packet`、`compile-images`、`compile-annotations` | 完整详情、原图/释读、台账编号 | 绑定 baseline SHA；原图、可见观察、推断分别表达 |
| 派生拆分 `DECOMPOSITION` | 授权范围内的Agent＋编译器；`source-item-decomposition/v1` | `decomposition-packet`、`compile-decomposition`、`review-revise` | 父项详情、Snn独立行、分析单元统计 | 绑定 baseline；KEEP/SPLIT/UNDO和前一派生工件需显式，不能靠目录增删子文件 |
| 分析策略与知识快照 `ANALYSIS_CONTEXT` | 用户/宿主策略＋程序；`reqpilot-analysis-policy/v1`、`project-knowledge-facts/v1`、`reqpilot-evidence-registration/v1` | `register-evidence`、`analysis-packet` | 分析内容区、协作区限制说明 | 项目知识共享；每次分析冻结实际目录SHA。plugin当前可传策略，不能传证据型评估/人工意见 |
| 响应评估 `ASSESSMENTS` | Agent＋证据校验器；`source-item-analysis-packet/v1`、`source-item-assessments/v1` | `analysis-packet`、`compile-assessments`、`review-revise` | 分析详情、Matrix响应列 | 绑定 baseline、decomposition、catalog和packet；无内部依据时是策略跳过，不是空评估 |
| 工程师意见 `MANUAL_DECISIONS` | 明确用户输入；`source-item-manual-decisions/v1` | `manual-context`、`import-manual-decisions`；应用已有持久化 | 条目响应、协作区、交付 | 独立版本/authority；不能由Agent评估冒充。plugin transport当前明确拒绝而非遗漏 |
| 来源/成果发现 `FINDINGS` | Agent/程序检测＋来源复核；**通用 schema 与保存命令待实现** | `audit-map` 目前只是只读投影；尚无共同 `save-finding/resolve-finding` | 统一发现入口、对象详情、交付未决摘要 | 需记录检查范围、scan state、source/result版本和处置依据；空数组不能表示已检查无问题 |
| 反馈与确认 `FEEDBACK_EVENT` | 用户、Agent自查、宿主回执 | `review-feedback`、`workbench-pull`；plugin `feedback/confirm-map` API；native确认/steer API | 固定Agent协作区、范围详情 | 绑定查看版和对象范围；已保存、已取回、已修订、已接受分开。当前portable/plugin/native schema尚未统一 |
| 同屏成果集合 `RESULT_SET` | 宿主注册器；**共同 schema/命令待实现** | plugin `version.json`、review `workspace-manifest.current` 是局部近似；没有统一入口 | 成果选择器、统一树/表/详情的 `viewed_revision_ref` | 固定每类artifact version；每个producer有自己的head，不按时间或revision数字静默合并 |
| 交付快照 `DELIVERY` | 程序导出；Matrix snapshot、`reqpilot-portable-delivery/v1`或`source-item-delivery-version/v1` | `deliver`、`review-close/verify`、plugin `export?revision`、native delivery API | 统一交付内容区、历史版本、下载 | 必须固定 result/baseline/source/snapshot SHA；草稿、FORMAL、人接受分别记录 |
| 执行与活动 `RUN_ACTIVITY` | native宿主、外部plugin报告、程序回执 | native task/job/SSE/steer/resume；plugin尚无统一外部运行报告 | 固定Agent协作区 | run失败不撤销已注册工件；外部未报告是UNKNOWN，不能从文件时间推断在线/完成 |

推荐把上述类型做成一份**代码级注册表**，字段至少包括 `artifact_kind`、允许的 schema/version、必需上游引用、validator、可选/必需、默认前端投影、可写 producer、敏感级别。当前 `workbench_tools.ARTIFACTS`、`plugin_workbench.ARTIFACT_NAMES`、`revision_tools.BASE_FILES/STATE_FILES` 和 `source_document_stages.STAGES` 应逐步消费同一注册表，而不是继续各维护一份文件名列表。

“固定类型”不表示每个文档都必须有全部工件。Map-only、部分 Items、无内部依据而跳过分析、只有历史只读交付都是合法结果集合；注册表负责解释缺失是 `NOT_PRODUCED / NOT_APPLICABLE / UNSUPPORTED / FAILED / UNKNOWN` 中哪一种。

## “已落地、已注册、可展示”的客观判定

| 状态 | 必须有的证据 | 不能据此宣称 |
|---|---|---|
| `PERSISTED` 已落地 | 内容已经原子写入；字节SHA/大小可回读；原件和工件都绑定真实source/version | 已被应用发现、已进入当前版本、语义正确 |
| `REGISTERED` 已注册 | 明确 `registration_scope=APPLICATION/PORTABLE`；对应DB或portable受控manifest中有不可变注册行，身份、artifact kind、schema、source/unit scope、producer、前驱和storage key通过校验 | 本地注册等于应用注册、前端已有adapter、用户看过、模型完成 |
| `PROJECTED` 可展示 | 统一读取API能按明确 `result_ref + artifact_version_ref` 返回；前端对应投影支持该schema并核对返回身份 | 完整、通过业务验证、人工接受 |
| `VERIFIED` 已验证 | 类型对应的确定性校验、来源回查或语义审查有具体收据和范围 | 全文都正确或用户接受 |
| `ACCEPTED/FORMAL` 已接受/正式 | 明确权限主体对指定版本和范围的不可变决定 | 可以覆盖原件、旧反馈或旧版本 |

`stage-results.json` 已指向某个task workspace文件，只能证明该native任务发布过一个可核对阶段指针；它没有跨任务/producer注册。plugin `versions/<revision>/version.json` 能证明该插件会话内不可变版本，但当前直接位于 application `object_root/runtime/plugin-workbench`，不在通用 DB 工件注册生命周期内。本地 review 的 `workspace-manifest.json` 有锁、hash head和不可变快照，是可靠的**portable范围注册/本地指针**，源码注释也明确它不是第二份 source ledger；它同步进应用后仍需应用自己验证并形成 `APPLICATION` 注册，不能把本地状态直接显示成“应用已注册”。

## 并行任务、多个 producer 与断点恢复

1. 每个写入先在 `runs/{producer_ref}/{run_ref}/scratch` 形成候选，经 validator 通过后再写不可变 object key并注册。目录扫描不得自动升级候选。
2. DB写入采用现有 extraction result 的思路：先创建 staging owner，写object store并核对SHA，再提交 artifact registration/result membership，最后CAS更新该 `work_ref + producer_ref` 的head。进程在任一点中断，reaper可根据staging/CAS决定补登记或回收孤儿；不能留下head指向缺失对象。
3. native与plugin可以基于同一source同时产出各自分支。两者都保留；前端恢复上次明确选择，未选择时列出可用结果。`native revision 14`与`plugin revision 3`没有大小关系。
4. 合并或局部修订必须生成新 `result_ref`，记录一个或多个明确 predecessor及其重放/重绑定收据。不能把plugin文件复制到native head，或用更新时间选“胜者”。
5. run状态与成果状态分离。运行失败、暂停或外部状态未知时，已注册Map/Items仍可展示；文件仅写到scratch且未注册时显示“存在未登记候选”或不对普通用户展示。
6. 反馈绑定它所针对的 `result_ref + map/baseline SHA + object scope`。新版本到达不改写旧反馈；处理回执再指出修订到哪个新结果。

portable review 当前的文件锁、临时文件＋`os.replace`、不可变 `reviews/<sha>.json` 和 `versions/*` 可以继续用于单工作区并发防护。原生应用已有PostgreSQL行锁、job lease fence、object staging/CAS和GC，应作为多进程事实来源。不要用portable的 `.review.lock` 代替服务端并发控制，也不要让Agent自己维护锁文件或恢复判断。

## 与现有存储的迁移策略

### 1. 原件与逻辑文档

- 保留现有 `sor_documents` 行、storage key和所有外键。新增轻量 `document_families`（即 `document_ref`）及 `sor_documents.document_ref / previous_source_version_id`，把每个现有文档先回填为独立family；只有有证据的同文件修订由用户或迁移规则显式归并。
- 当前 `sor_documents.id` 继续充当 `source_version_ref`，避免重写全部既有artifact外键。以后上传“同一文档新修订”时新增行，不更新旧行source SHA。
- 新增 `document_units` 时从已核验Map根/来源范围生成候选，默认先建一个“整份原件”unit；不能把所有现有Map多根自动解释成多个独立文档。

### 2. object store与工件注册

- 复用 `stored_objects` 和 `extraction_result_artifact_managed_objects` 的不可变对象、引用、staging、CAS及GC设计；不移动或重写现有对象字节。
- 新增通用 `document_artifact_versions`、`document_result_versions`、`document_result_members`、`document_result_heads`。artifact记录持有kind/schema/source/unit scope/producer/run/predecessor/storage metadata；result固定成员集合；head按 `work_ref + producer_ref` CAS推进。
- 现有 `extraction_result_artifact_references` 以 `job_id` 为唯一引用，适合提取job结果但不足以承载任意工件类型和多版本成员。可让它继续做原job所有权，通用注册表增加业务引用，不强行改变其生命周期职责。
- `agent_structure_working_revisions` 和 `source_item_delivery_versions` 已是不可变版本。迁移时为其补通用注册记录，原表继续作为专项权威/兼容读入口，验证新旧读取一致后再决定是否收敛。

### 3. plugin 与 portable review

- 对 `object_root/runtime/plugin-workbench/**/head.json` 做一次只读扫描：逐版验证 `version.json.files` SHA、source绑定和前驱链，按 `EXTERNAL_PLUGIN` producer回填注册表。无法验证的版本保留原路径并标 `LEGACY_UNREGISTERED`，不猜测成功。
- 后续plugin同步先走通用object-store写入和注册服务，`head.json/version.json`只作为兼容投影；版本读取逐步改为由注册表物化。`workbench_tools.py` 仍负责本地传输与反馈取回，不成为服务端真相源。
- portable `workspace-manifest.json` 继续作为可携带、本地不可变review head。`review-open/close/verify` 无需删除；`workbench`同步时把经过验证的具体工件注册到应用，保存 `local_review_sha256` 作为provenance，而不是上传一份manifest后直接相信其“current”。

### 4. native阶段与前端

- `source_document_stages.py` 先保持兼容，但 `publish_stage` 在写 `stage-results.json` 的同时调用通用注册服务；阶段文件改存 `artifact_version_ref/result_ref`，路径仅用于该task恢复。只有DB注册成功的工件进入统一成果选择器。
- `SourceDocumentStageResults` 继续显示Map-only/Items阶段草稿；`NativeStructureReferenceDock`、`SourceLedgerTable`、详情和导出改从同一result投影读取。前端不扫描目录，不按URL参数、provider名称或存在`sourceReader`推断能力。
- 新的工作区读取API返回专项主稿已定义的 `work_ref/result_ref/producer_ref/task_ref/viewed_revision_ref/latest_revision_ref`、capabilities及“已落地/已注册/可展示”状态。历史adapter仍可返回只读结果，不需要先迁移所有旧数据才能统一外壳。

## 最小可实施增量

建议把首个增量限制为“一个现有PDF、native与plugin各一份已保存结果，可从同一工作区明确选择、恢复和导出”，不先做整个目录搬迁。

1. **集中类型注册表**：新增代码级artifact registry，先覆盖 `DOCUMENT_MAP / TABLE_PREVIEWS / SOURCE_LEDGER / VALIDATION_RECEIPT / ANNOTATIONS / DECOMPOSITION / ANALYSIS_CONTEXT / ASSESSMENTS / MANUAL_DECISIONS / DELIVERY_SNAPSHOT`。让现有三份文件名清单消费它；未知工件继续fail closed。
2. **最小身份表**：新增 `document_ref` 与通用 artifact/result/version/head表；现有每个 `sor_document` 自动拥有一个family。先不提供自动同文档归并，但schema从第一天允许 `previous_source_version_id` 和 `unit_scope_refs`。
3. **一个注册服务**：提供事务化 `register-artifact`/内部API，校验source、schema、SHA、前驱和producer；复用object staging/CAS。该真实命令当前**待实现**，不能先在Skill里宣称可用。
4. **双adapter回填**：native `publish_stage` 与plugin `sync_plugin_draft` 在不改变旧版本的前提下注册Map和baseline结果；portable review只通过plugin/host适配进入。注册失败保留原工件并返回“已落地、未注册”，不假装前端可恢复。
5. **统一只读投影**：增加按document列result、按result读工件和capabilities的接口；P2前端先接成果选择、Map/Items和同版草稿导出。现有工作台组件继续负责显示。
6. **断点与并发验证**：至少覆盖object已写但DB未提交、DB staging存在但object未写、两个producer同时推进各自head、同producer陈旧head CAS、重启后恢复、旧反馈仍绑定旧result。
7. **第二切片再补**：同文档新原件修订、一个文件多个document unit、通用finding保存/处置、完整分析/人工意见plugin传输。目录物化CLI可以在注册表稳定后增加，避免先固化错误模型。

### 正例

- plugin提交Map和Items；宿主逐个校验schema/source SHA，写object并注册为一个不可变 `result_ref`。页面显示“plugin v3，已注册，可展示，人工未接受”；native v14仍在同一选择器中，不被覆盖。
- PDS修订版上传到同一`document_ref`，得到新`source_version_ref`和SHA；旧版反馈、交付与原件仍可打开。新Map引用前一来源版本只作为差异/重绑定依据，不沿用旧版“已确认”。
- 一份PDF包含PDS和独立试验大纲；程序注册两个`document_unit_ref`，同一SourceIR只存一次。两个Map范围可分别修订，项目知识共享；合并交付明确固定所含unit和版本。
- native任务在保存Map后失败。Map对象和注册记录完整，run为FAILED，前端仍可打开阶段成果；未完成Items显示NOT_PRODUCED而不是0条完成。
- 用户针对plugin v3的SRC-001提交意见。v4到达后，意见仍显示“针对v3，plugin报告已在v4处理，待用户核对”，不会自动改成已接受。

### 反例

- Agent创建`01-reading/02-map/03-items/04-analysis`并把文件移到下一目录表示阶段完成。
- 上传同名`PDS.pdf`后覆盖旧文件、复用旧source SHA字段，或只按文件名自动判为同一文档修订。
- 服务启动时扫描目录，以最新mtime或最大的`vN`决定当前成果；native v14因此压过plugin v3。
- 看到`document-map.json`存在就显示“结构已保存”，没有校验SHA、schema、source和注册回执；或看到页面能渲染就标“提取完成”。
- Agent直接编辑`workspace-manifest.json/head.json/results/*.json`，声明所有工件已生成；程序只做目录存在检查。
- 每个文档复制一份`knowledge/current/`，后来按文件时间选择内部依据，导致旧分析无法证明当时使用的KB版本。
- 将一个PDF的每页建成document unit，或把独立附件硬塞进主文档章节，只为适配目录树。
- native和plugin同时写同一个“latest”文件，后完成者覆盖先完成者；失败run清空已经注册的旧成果。

## 是否存在更简单的替代方案

**有，而且对原生应用应优先采用：不创建长期可见的真实“项目/文档文件夹”，只实现DB工件注册表＋object store，并在Agent任务或导出时按上述目录临时物化。**

这是比“每个文档长期维护一棵文件树”更简单、更稳的方案：现有应用本来就是数据库/object store架构；前端只需要查询result和artifact，不需要访问文件系统；权限、并发、GC、备份也继续走既有机制。portable plugin与冷启动workspace仍保留真实目录，因为它们需要跨宿主携带、离线审阅和Agent可读性。

如果当前只想解决P2工作台，不必先实现同文件修订和多document unit的完整UI。可以先以现有`sor_document_id`作为临时`document_ref + source_version_ref`的一对一映射，完成类型注册、双producer结果选择和统一投影；但数据库字段与API命名必须保留两者区别，不能把这个过渡映射固化成产品语义。

不建议的“更简单方案”是只统一目录名、只新增一份大manifest，或让前端扫描文件夹。这些做法代码量少，却无法处理服务端并发、不可变版本、同文件修订、多个producer和旧客户成果，最终会形成第二真相源。

## 决策建议

将该理念纳入P2，但把交付目标写成：**“统一工件注册与工作区投影”**，而不是“建立固定步骤文件夹”。首轮只实现类型注册、不可变结果集合、native/plugin双适配和前端显式选择；目录树作为portable/Agent任务的机器生成视图。`document_ref/source_version_ref/document_unit_ref`从数据合同中先分开，修订与多单元能力可以后续启用。这样既获得PPT Master式的可发现、可恢复工作区，又不牺牲ReqPilotX已有数据库、来源保真、并发和版本边界。

## 主任务的采用决定（评估完成后）

用户已授权并行实施既定P1/P2。本任务采纳稳定文档身份、固定工件类型和机器生成目录/索引，但首个切片继续复用现有注册与不可变版本；新增通用artifact/result表和document family/multi-unit关系作为后续设计候选，不成为恢复统一工作区的前置。固定文档目录尚未批量创建，也未新增workspace-init命令。评估时尚未存在的`source-findings/v1`现已在首批业务实施中作为有范围的检测报告生成；通用发现处置注册仍待实现。进展见[业务实施记录](统一工作流与工作台专项-业务实施记录.md)。
