## 方法与工具

业务skill维护源仍在`agent-assets/current/plugin-skills`，通过catalog及现有投影脚本同步到插件，未改vendor或兼容Agent Kit。

- 纯标题没有可独立分类的陈述，保留为结构；标成`NON_REQUIREMENT/HEADING`也不因此需要SRC。定义或适用条件即使加粗，仍是正文。补了简短正反例及“Map把标题放进正文时先修角色”的实际路径，避免靠制造SRC通过编制。
- 同一总成的壳体、密封和紧固件是完整BOM内部组成。不同零件名、数量、行号或制造备注，不自动证明是独立BOM分支。来源明确区分的独立配置/供货清单才提供分开分析的依据。保留内部原编号，不为了编号拆SRC。
- 自查增加上述两个检查点；按需读取对应例子，不要求每次加载全部reference。未新增自动判断正文语义、分类或表格分组的算法。

工具端由程序返回实际可调用入口：

- task open/inspect等摘要在已有Map时给`scope_read`，已有Items时给`source_items_read`，避免接续预制阶段后重新寻找目录和schema。
- 无效scope part、缺scope、未知scope、缺原文ref以及尚无Items等导航错误，按实际状态给`next_action`。表格仍通过其返回的真实fragment请求读取，不接受猜测的`cells`等别名。
- 无效schema位置返回绑定当前schema的定义目录入口；`part:definitions`从实际REQUESTS生成名称和读取请求，不补造模型猜测的类型。
- 显式过期Map、任务观察版本、schema身份仍被拒绝。恢复只读取索引/证据，不替换scope、不提交判断，也不推进任务版本。

涉及代码为`task_reading.py`、`task_read_resolution.py`、`task_schema.py`、`task_service.py`和MCP描述；新读能力标记为`read_navigation_recovery`。历史任务仍使用其固定包，本文不宣称旧安装已有新入口。

## 新候选实跑结果

私有根`evals/luna`、`evals/qwen`使用同一候选和既定来源。开始前核对877个来源节点与Map编译捕获逐字节一致；恢复原有评测数据库/对象目录及18081服务后另建项目、文档，未替换历史任务。两运行均自然结束，期间没有操作者改输入、代填参数或修模型成果。

| 配置/宿主 | 自然结束 | 首次Items | 实际交付 | 来源评核 |
|---|---:|---:|---|---|
| Luna Max / Codex CLI + MCP | 1762.471秒（29.4分钟） | 933.897秒 | 11 SRC / 6 REQ，同版工作台与登记Excel | FAIL：里程碑过度合并，完整试验按方法/判据分开 |
| Qwen High / Pair headless CLI + MCP | 4457.728秒（74.3分钟） | 2863.955秒 | 10 SRC / 4 REQ，同版工作台与登记Excel | FAIL：里程碑过度合并；完整试验保持正确 |

两者都自主修正了纯标题的Map角色，并保留完整BOM；相较前轮这是具体已观察到的改善。但独立里程碑被合为一个条目的共同偏差仍在，不能称方法已经稳定。Qwen的判定理由明确引用T05，而reference的“保留整体业务组织”位于业务单元选择表中，可能诱导整表合并；这是有线索的框架问题，尚不是独立因果试验结论。下一轮不能只继续追加针对单一失败的例外。

现有冻结rubric共19项：Luna为15 PASS、1 FAIL、2 REVIEW、1 N/A；Qwen为14 PASS、1 FAIL、3 REVIEW、1 N/A。一个粒度判据可包含多个实际问题，不能用FAIL数量减少宣称质量提升。来源复核由操作者执行，未冒称独立冷评核或工程师接受。

此外单列了原编号字段缺口：原序号仍在原表/标题里，两者的表格条目却未绑定原编号集合；Luna拆开的试验也没有原编号。Qwen正确绑定了完整试验的标题编号。未把字段缺口误报成原文字节丢失，也未偷偷增补冻结rubric计分项。两者的工作台快照与本地快照完全相同，Excel业务内容一致，差异仅限显示文件名前缀和导出时间；这也说明语义问题来自上游编制，不能归咎于导出。

Qwen保留了一项“捕获范围内未找到术语定义”的未决说明，但自查记录随注释修订自动标为ADDRESSED。文字仍在，状态语义需另行核查，不能将工具自动关闭行为完全归给模型。程序完成、未决保留和工程问题解决要继续区分。

## 效率与运行限制

- Luna有137次公开工具调用、20次失败；其中9次来自同批`limit=200`超过上限，6次猜schema名称，3次使用旧上下文读取版本，另有一次本地路径错误和一次Map字段冲突。不是20轮同一种卡死。
- Qwen有63次公开工具调用、5次失败；随后均有继续推进，最终自然结束。另有一次公开`TRANSPORT`重试，不能称为空闲超时。过程中的口头误称已纠正。
- 公开工具执行区间并集约77.558秒、52.116秒。其余时间包括模型、服务端、网络和宿主等待；缺少HTTP发送/首delta分段，不能直接归为纯思考或单一harness原因。
- 两宿主发现的MCP工具schema合计68009个JSON字符，值得研究按需发现与紧凑返回；字符数不是token数，也不是已经证明的耗时原因。
- 运行期间另一Pair任务报告了独立原生应用验收。该路径当时只有固定CLI，案例也不同；后续正在接MCP。并发provider请求、宿主接入与案例差异已记录，不把本线结果当作Pair原生应用性能或模型排名。
- 本次代码/skill同时改变，是组合版本评测，不是纯skill A/B或原件冷启动。两个配置各一次运行，不作统计性加速结论。
