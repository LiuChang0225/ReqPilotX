# MCP 与业务接口：Pro 评审后的实施

更新：2026-09-13。用户要求通过侧边栏 ChatGPT Astra 6 Pro 独立判断，若可行继续执行。本轮实际核验页面为 **6 Pro**，上传完整材料后只发送一次；完整答复已读取，结束标记通过，页面已停止生成。

## 评审结论与采用方式

[ChatGPT 完整评审](https://chatgpt.com/c/6aa5f2f8-8e74-83e9-b573-cd25e630f863)共17,767字符；本页是经本地核验的摘要，不冒充逐字全文。提供给Pro的是13,998字符材料，含业务背景、现状、评测摘要、skill/工作区合同及精确代码摘录；没有完整仓库、客户原件、凭据或原始日志。Pro明确说明了材料边界。

采用的主要结论：**业务合同先行，固定 CLI 子进程桥接，薄的本地 stdio MCP 保持可选。** 不建设新 Task Service 进程、数据库、队列或 Agent 编排层。

| 意见 | 本地判断与行动 |
|---|---|
| 机械字段、路径、状态和结束判据的优化，不能全归因于 MCP | 采用；新的 typed task API 同时提供给 CLI 和 MCP，业务实现相同 |
| 保留每个任务固定的运行包 | 采用；MCP先验证任务记录与原件，再选择固定CLI；旧包缺新能力则明确返回不支持，不静默升级 |
| 版本前提必须到核心提交层，幂等不能靠 JSON-RPC ID | 采用；核心增加调用方revision、持久command_id和creation_key，保留原最终CAS与候选规则 |
| 原远端隔离可能不足 | 核对后发现现有binding校验、session隔离、远端版本CAS和过期producer保护已经存在；不重复重构，修新facade绕过校验的地方 |
| 提交、同步、导出、登记和核验不能压成一个成功位 | 采用；后置核验失败保留已提交工件和操作回执，分别返回状态 |
| 先用官方SDK并验证真实宿主 | 采用；官方Python SDK锁定2.2.0，使用隔离环境，验证自动发现与legacy握手路径，不手写协议 |
| 保持读取自由、减少局部编制负担 | 采用；复用原逐页MD/高清图、原文/表格/坐标和增量编译；普通段落预算够就完整返回，超长块和大表可续读 |

Pro提出的九个工具名字是设计示意，不是必须再建立一套业务模型。当前接口从已存在的Map编辑器和Items候选类投影，保留原文包含、Snn派生、引用与原编号的既有定义。

## 已落代码的职责

- `task_contracts.py`：Map编辑typed输入，文本/表格Items判断；程序补摘要和scope相对offset，保留稳定item_key/record_key。
- `task_reading.py`：复用原读取能力，提供预算内文本、结构化表格分页、准确scope、页Markdown和校验过的PNG；无阶段页白名单。
- `task_service.py`：协议无关的应用入口；任务定位、真实简报、原工作区编译、自查、交付和工作台调用。
- `task_bridge.py`：执行前核验任务记录，调用任务固定CLI；捕获日志，超时停止进程组并报告UNKNOWN，不假装回滚。
- `mcp_server.py`：官方SDK stdio适配；按具体业务操作提供schema，返回结构化状态和真实image内容块。
- `task_workspace.py`、`workspace_tools.py`：在现有操作记录中补版本前提、命令重放和创建重放，保留原保存/发布/登记路径。
- `task_workbench.py`：同作用域的工作台内容核对、登记后当前review的明确补同步；不放宽旧producer保护。

现有CLI仍可直接使用；新`reqpilot.py task ... --input <file>`或`--input -`接受相同请求。MCP替Agent创建传输输入文件，业务层再次冻结实际编制依据。

## 本轮新增保证

同键同输入重放原操作；同键异输入拒绝。先找已执行请求，再检查旧revision，避免把自己上次成功提交当成新冲突。STARTED而没有完成证据时不自动重跑；已保存回执可按原CAS恢复索引。创建请求重放不另建任务，也不重复可选HTTP连接。

读取→开工间隙的版本变化在核心锁内拒绝；编译过程中变化仍由原最终CAS保存候选，不覆盖新head。任务记录先验证后选可执行入口。

本地已经COMMITTED时，后置核验异常单列，保留operation、receipt、output与Excel。核验使用`verify_review`返回的同一个review和delivery，并核对当前状态；不会把两个版本拼成“可交付”。

工作台内容匹配需要来源、项目、文档、session和任务binding正确；相同SHA或相同矩阵不足以跨任务匹配。实际渲染仍单列，HTTP内容一致不是浏览器截图验收。

## 第一版范围（023533历史记录）

当前提供任务创建/接续、检查/恢复、来源准备与阅读、Map局部编辑、新范围Items、review准备、程序交付、反馈拉取和补同步。无内部依据时，显式`analysis_policy:"skip_no_internal_evidence"`使用已有SKIPPED政策；默认保留已有政策。

已覆盖范围的revision、图像释读和Snn编制继续使用既有CLI/review能力，本MCP预览尚未逐项暴露；完整人工意见和证据分析传输仍未实现。普通工具请求取消不代表业务副作用回滚；无在途lease恢复或后台任务调度承诺。该版本不自动替换默认CLI或迁移旧工作区。

使用方式与调用样例统一在[插件task API指南](../../plugins/reqpilot/skills/reqpilot/references/task-api.md)。SDK安装、工具发现、程序重放、模型读取和语义质量分别验证。

## 修订与图像增量（035049）

当前安装包`0.3.0+codex.20260913035049`已补齐以上三类入口，CLI/MCP仍共用业务实现：

- `task_change_contracts.py`绑定已有SRC、确切引用、图像归属、scope替换与拆分判断；程序填写packet/hash/offset，保留稳定key与原始覆盖校验。
- `task_change_reading.py`、`task_item_views.py`返回当前条目的完整原文、共享表头、图片关系、释读与拆分packet。普通条目一次读完，长JSON先转换公有续读链接再分块；图片实际返回PNG，不以路径冒充已读。
- `task_review.py`把真实发现登记、编制、程序导出、关闭review及同步组织为一个持久命令。已有原子步骤和CAS继续生效，丢失响应只认准确的原请求及已保存阶段回执，不创建另一条HEAD。
- `task_changes.py`区分初始overlay与已有review修订。相同命令的历史路由固定，进入review后重放早先overlay命令不会重新编制或改换路径。
- `workbench_sync pull`把当前工作台实际反馈导入当前review；主动自查可连同修订提交`self_review_finding`，程序登记真实`AGENT_SELF_REVIEW`编号，不要求人为创建文件或虚构USER反馈。

一次命令只收敛机械编制，不替Agent决定分类、图像含义和粒度。独立图可建立IMAGE条目；表内图始终属于表格条目，释读与逐字原文分开。图片释读支持新增/更新，未引入空文本撤回；纯图片无原生文字范围时，不以释读伪造逐字Snn。

实机又发现一个需收敛的经验：父项分类变化后，已有规则会使旧派生进入待重评，UI正确显示，但任务返回此前不突出待办。现`pending_decomposition`直接列受影响父项、原因和当前版本读取入口；存在明确未决范围时`handoff_ready=false`。重新判断后恢复原Snn身份，而不是偷带前版派生或以Excel存在宣布完成。

确定性程序证据在`prototype/runtime-data/mcp-review-implementation-20260913/`：

- `live-complete/result.json`：冻结同一原件、新任务，真实MCP→18080反馈→分类修订→派生重评→同版Excel，全链通过，10 SRC/9 REQ/2 Snn，`S01/S02`保留；完整工作台snapshot与本地相同，1362格仅实际ExportedAt相差3秒。旧保护v3前后未变。输入是合成原件和显式测试判断，不计模型成绩。
- `live/verification.json`保留早期034152联调：核对器最初错用ExtractionMeta而不是实际_ReqPilotXMeta，导致仅导出时间差异被误判；原失败result/log保留，后续只读复核，无业务重跑。该版分类后派生待重评的事实也保留，不能当最终2Snn闭环。
- `sdk-tests-complete.log`：3项真实SDK测试，包括CLI/MCP同判断、图片内容块、修订后待重评及保留Snn；`task-tests-complete.log`为59项聚焦回归，`core-tests-final.log`为30项核心回归。测试组合可能重叠，不相加为文档数量。

现有工作台已实机显示表格条目、原表单元格图片和独立Agent释读；未改前端。模型是否更快、更准继续由同包冷启动对照回答，不能用这些程序集成结果代替。

## 评测口径

历史92411的Sol high/Luna max成绩保留，不能直接拿它对新MCP算速度提升。下一轮比较应在同一冻结新包中区分：

| 对照 | 可回答的问题 |
|---|---|
| 当前粒度CLI C0 vs typed CLI C1 | 业务接口和机械参数收敛是否有效 |
| typed CLI C1 vs 同接口MCP M1 | 直接工具调用与宿主呈现增加了什么价值 |
| C1/M1各自再配同一改进skill | 提示词/参考的增量，不混算协议收益 |

先做无模型确定性重放：来源、判断和核心相同，比较原文、编号、父子/表图关系、工件与状态，排除合法的任务ID/时间差异；再做Sol high/Luna max各自的新会话对照。只统计真实调用、保存/可见/完成时刻、错误与修正类别、完整用量；不把帮助查询数当浪费时长。

真实留出PDF、多次独立运行和实际图片输入仍是推广依据。当前代码与协议通过不意味着已证明Luna更快或MCP提高语义质量。

### 宿主写入预检缺口（本轮实际发现）

035049首轮四格已实际启动；M1的Sol/Luna在`task_open`遇到宿主拒绝：工具需要审批，但运行策略为never。SDK发现、stdio重放和宿主只读图片探针均不能证明宿主允许写入。两次M1于约191/192秒由主任务停止，保留原公开事件、退出与实际产生状态，归为HOST_POLICY_INVALIDATED，不评价模型提取能力；两次C1继续原运行。

按照[官方MCP配置](https://learn.chatgpt.com/docs/extend/mcp)，审批可按服务器的具体工具配置。新的测试准备只给本轮已授权、本地隔离作用域中的写入工具设置调用级`approval_mode="approve"`，不改全局配置、原件、包、沙箱或工具真实读写标记。另开短Luna max预检，实际走task_open→capture→inspect；通过后再以同035049、相同业务prompt与新任务重跑M1。原四格harness/工作区冻结，新准备入口是私有`cold_matrix_authorized.py`，不能覆盖旧失败记录。

评测经验：环境资格至少分SDK协议、宿主读取、宿主写入与工作台网络四层。付费整文前应验证本轮实际宿主中的最短写入路径。发现环境拒绝时及时停损，禁止把Agent寻找备用调用方式的耗时计成模型能力或MCP收益。

短Luna max宿主预检已于75.105秒结束，真实3次MCP调用全部完成、终端调用0，见`host-write-preflight/verification.json`；它不计整文成绩。修正宿主配置后的M1两次整文在`cold-matrix-authorized-035049/`新任务启动；C1保留原suite，二者bundle、业务prompt、skills与原件SHA不变。各格共用主机、一次运行，仅作探索性对照。公开tool events包含started/completed，调用次数由`analysis/execution_metrics.py`按thread/item.id去重，不把一个调用算两次；原始harness统计和失败记录均保留。
