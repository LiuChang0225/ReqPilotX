# 统一工作流与工作台专项：UI 协作意见

更新：2026-09-12。状态：**只读审计及接口建议，尚未实施本专项。**

本文件是[专项主稿](统一工作流与工作台专项.md)的 UI 侧评审与消费合同建议，不另立执行计划。职责和优先级以主稿及[唯一开发计划](开发计划.md)为准。仅检查当前代码、已有接入记录和指定的 18080 合成联调界面；未修改实现、v1/v2/v3 或反馈，未启停服务、运行测试/新模型评测，也未提交新的确认或意见。

## 结论与对主稿的意见

支持主稿的责任划分和 P1/P2 交叠：业务任务负责真实原编号、统计、发现、范围、版本及执行适配；UI 任务负责统一外壳、路由、视图、协作区与交互。**协作入口属于文档工作区；某个按钮能否执行、执行到哪里、产生什么效果，由 provider 的真实能力决定。**

当前问题的主要原因是状态和控制权没有统一。`PluginWorkbench` 已经复用原表格/详情/PDF，但仍替换整个文档外壳；它没有进入 `DocumentAgentContext`。同时，内层组件将“存在 sourceReader”当作关掉 native 控制的条件，却没有相应的外部协作模型。因此界面复用和执行隔离都做了一部分，用户仍感受到两套产品。

建议在主稿落实时补明确以下边界：

1. **固定的是协作入口、上下文和区域位置。** 宽屏停靠，窄屏与主区切换；折叠不丢任务、草稿或版本。不要把“固定”理解成永久占用列宽，也不要在每个阶段强制放一张审批卡。
2. **同一文档可有多个真实成果来源。** native v14、插件 v3、历史锁定 Set 的版本号没有跨来源大小关系。默认入口优先恢复用户明确选定的工作/版本；多个来源并存且没有选择记录时，明确列出可选成果，不按更新时间或 native 优先级静默换稿。
3. **页面目的与 producer 分开。** 点击分析、交付仍进入相同外壳下相应的内容区。外部能力不足时在该内容区解释限制，不能把“交付”导航渲染成“需求提取”页面。
4. **P2 可以先接现有可证明的动作。** 外部保存反馈、确认 Map、查看/导出快照已经有接口；自动唤醒外部对话、分析/人工依据完整传输不是恢复协作区的前置。缺少运行报告时显示未知，不能补开 native 模型来制造进度。
5. **旧入口退出日常路径与旧数据迁移分开验收。** 先保证旧客户版本、意见、来源定位、导出及深链接可回查，再移除重复壳。不得将“统一”实施成一次重跑、重编号或重签全部成果。

## 2. 统一外壳与固定 Agent 协作区

### 外壳与选择状态

整个文档任务只挂一个文档外壳、一个主内容区和一个协作控制器。上传后、仅 Map、完整条目、分析、交付及历史查看都在这里变化内容，不因 producer 替换页面树。

主区和协作区共享以下绑定，且每个命令带回服务器核验：

- 项目、文档、原件 SHA。
- 当前选定的工作/成果来源；其真实 producer 引用和任务引用分开，任务可以不存在。
- **正在查看的版本**与**服务器最新版本**分开；Map、baseline、派生、分析和人工响应版本不压成同一个整数。
- 选中的结构节点/SRC/Snn、原页位置及操作范围。

URL 负责可恢复的导航和深链接；不承担权限判断。`pluginSessionId`、`requirementSetId`、`reviewCase`先经一个解析边界转成明确 work/result scope，再决定适配器。缺失/互相冲突的身份不应静默降级为另一份结果。用户在文档任务间导航时，保存查看版本、选中对象和未提交草稿；切换项目/文档则重新验证作用域。

多个来源并存时恢复上次明确选择；无记录则展示清楚的成果选择。原生当前工作版和外部不可变快照可以共用界面，但不自动合并内容或接管对方任务。

### 协作区的固定信息顺序

1. 当前任务目标、真实执行来源、最后报告/同步时间。没有目标显示“未提供任务目标”，不生成一段文本冒充用户委托。
2. 实际需要用户处理的事项：指定 Map 确认、来源疑点、版本冲突等。只有真实需要决策时才出现 Approval Card；确认动作明确绑定哪一版、确认后发生什么。
3. 已保存成果入口：结构、条目、草稿交付；打开后改变主区内容，保持外壳与协作。
4. 公开进展及处理记录。每条保留 producer、任务、时间和版本来源；没有外部消息时明确只有同步记录，不借用另一任务的轨迹。
5. 绑定当前对象的输入与可用动作。保存反馈、人工响应、确认结构、启动/续接是不同命令，不全部变成一条聊天消息。

分析被策略跳过时显示“未执行：未提供内部依据/本次跳过”；尚未整理的授权范围显示待处理；接口不支持人工响应显示该入口限制。三者不混写为“尚未分析”。

### 外部插件无法自动唤醒时的具体行为

| 实际情况 | 可以显示和提供的动作 | 不应声称 |
|---|---|---|
| 只收到外部成果，外部运行状态未报告 | 目标（若提供）、已保存 v3、最近同步、查看成果、记录反馈、复制接续说明 | 正在思考、正在处理、任务已结束或已离线；仅靠更新时间不能判运行状态 |
| 反馈接口已经保存成功 | “意见已保存，待外部任务取回”，保留反馈ID、原版本和对象 | 已送达外部 Agent、已开始修改 |
| 外部任务实际报告已取回/执行 | 展示该回执与时间；可展示真实进展 | 没有回执时推断已消费 |
| 插件报告修订并提交 v4 | “外部任务已提交修订，待核对”，提供成果/改动引用；原 v3 意见保留 | 工程师已接受、问题已经完全关闭 |
| 可以识别原对话且宿主支持打开 | “前往外部任务”；若仅能打开，就只说明打开 | 点击后已恢复模型执行 |
| 不能识别或打开原对话 | “复制接续说明”：包含可用工作台链接、当前版本和待取回意见；工程师回到原任务继续 | 用无效按钮、手填长ID或启动新 native 任务代替接续 |
| 确认 Map 的回执仅解除插件后续条件 | 按钮“确认此结构”；成功后“确认已保存，待外部任务取回后继续” | 用“确认并继续”暗示已经启动后台任务 |
| 明确可控制的 native 当前运行 | 按真实能力提供补充、暂停、继续；沿用现有线程/回执 | 因插件不支持某动作而删除 native 已有控制 |

P2 不需要自动唤醒外部对话。**外部任务已结束时，不能为显示协作区而补开 native 模型，也不能拼接两份执行历史冒充连续任务。** 即使所有执行控制不可用，协作入口、真实成果、反馈记录及接续说明仍然有用。

历史只读成果也保留这个入口，显示“历史成果/无可控制任务”；由能力合同说明哪些动作能做。不要用“无运行任务”推断“无已有成果”。

## 3. 两种视图、原编号与计数建议

### 使用方式

建议将显示方式命名为 **“条目台账”** 与 **“原页对照”**，保留当前实现中的表格、结构导航、完整详情和 PDF。说明放在切换按钮提示里，不再占一整行常驻文案。

| 显示方式 | 默认场景 | 用户动作与保留信息 |
|---|---|---|
| 原页对照（现“结构与原文”） | 初次核对结构、归属、遗漏、跨页、原表/原图；台账遇到疑点时回源 | 结构导航＋完整详情＋原页定位。当前对象和查看版本保持，不重新执行提取 |
| 条目台账（现“表格审阅”） | 有条目成果后逐项/跨项检查编号、分类、派生与响应 | 完整父条款在前，Snn逐行跟在父项下；筛选保留必要父级路径。选中行和详情/反馈/来源位置一致 |

推荐先做结构核对，再用台账逐项审阅，遇到疑点局部回源。阶段表示成果是否已形成/需要确认；视图只是当前成果的看法。不要再增加一层同义步骤条。已有 Items 的文档默认进入条目台账；仅有 Map 时进入结构核对。新版本到达仅提示，不强行抢走正在核对的旧版本。

切换视图必须保持 `viewed_revision + selected object + filter + source location + unsent draft`。不得因为从表格切回原页就回到另一个 producer、最新版本或整份文档范围。全部展开/收起只影响显示，不改变业务计数或导出范围。

### 编号和列

建议台账把“客户原编号”和“系统标识”分清：原编号靠近正文且始终可见；REQ/SRC放次级字段，派生项显示Snn及其父来源。可以采用“原编号｜内容与层级｜系统标识/类别｜响应与发现”，窄栏则将原编号置于内容行首，不以隐藏编号换密度。

直接消费共用 Matrix 的原条号投影及其证据：`source_number`、原文项的编号集合/角色、派生项的 `source_number_projection`。UI 不从英文概括、正文前缀、REQ编号或相邻行做正则推号。

- `2.6`、`2.10`和`V-01`按原件显示，保持原序。
- 无独立编号的 Operating conditions 显示“无独立原编号”，同时保留第2章路径；不显示伪造“2.0”。
- 多编号整体显示原条号集合并可展开对应依据；保留BOM/完整试验整体规则。
- Snn 的客户来源号可以仍为2.5，但明确标为父条款来源；S01不能转写为原件不存在的2.5.1。
- 结构行的章节号不是该章每一个直属正文的独立原编号。

编号异常由业务侧产出候选、回源发现与处置工件。UI只展示状态、依据和操作入口：未回源时“当前成果编号间断，待核对原页”；回源确认原件确实跳号后“原文2.6后为2.10，已保留原编号”。原页存在而成果缺失才表示提取遗漏。提示不自动补条目、不改号、不阻断其他有效成果。

### 计数

| 口径 | 推荐显示 | 约束 |
|---|---|---|
| 当前章节子树 | “已保存原文8 · 其中需求8” | 唯一SRC计数；折叠、结构1:1共行都不改变。若检查范围不完整，不能称为整章应有总量 |
| 直属内容 | “本层直属正文1项”放提示或详情 | 本例为Operating conditions；不用裸“1条”代替章节总量 |
| 工程派生 | “派生2项” | 两个独立Snn；不增加原文SRC数量 |
| 实际分析单元 | “分析单元9” | 本例8−1＋2；不把派生父项重复算入响应分母，也不以多数/平均给父项汇总符合 |
| 当前筛选 | “匹配原文X / 已保存Y”；需要时另列命中Snn数 | 匹配数、可见行数和业务总数分开；父级上下文行不冒充额外命中 |
| 发现/待处理 | “未决发现N”“待响应N”分别显示 | 编号间断可能涉及两个端点和一个发现；不能用“受影响条目数”代替“发现数” |
| 覆盖/未知 | 已保存范围、未处理范围、检查是否完成 | 未评估总量为未知，不显示假0或假100% |

这些统计由共用业务投影给出或按同一明确算法派生，不能在树、表、插件适配和Excel各算一遍。此前W09已由业务侧复查并撤回，不作为实施依据；UI仍需区分编号投影缺失、原件跳号与提取遗漏。

## 4. P2 最小服务端字段与动作名单

以下是 UI 首个纵向切片的依赖，属于主稿最小合同的具体化。**不要求先新增一套业务数据库或替换既有接口。** 可以由现有 native/plugin API 的服务端投影/适配统一返回；前端约定一份类型和行为，由业务任务实现服务端/工具侧。

### 首个切片必须具备的读字段

| 字段组 | 最少字段/语义 | 当前可以复用与需要补的地方 |
|---|---|---|
| 工作与查看绑定 | `project_id, document_id, source_sha256`；稳定 `work_ref/result_ref`、`producer_ref`；`task_ref`可空；`viewed_revision_ref`、`latest_revision_ref`、可用版本/阶段 | 现有task/session/Set/工件引用可规范化，不要求伪造新任务ID。一个显式解析入口处理多来源选择；冲突选择不能静默丢弃 |
| 版本依据 | 显示序号、真实revision ID、Map/baseline/派生/分析摘要、人工响应revision（未支持可空） | 不把plugin v3、baseline revision、delivery version混为一种版本号。记录/动作/导出使用同一查看依据 |
| 任务与同步摘要 | `goal|null`、执行状态及报告来源、`last_reported_at`、`last_synced_at`、已有成果、已保存/剩余/未知范围、待输入事项 | native已有部分字段；plugin head保存goal，但当前`_public`未返回，UI也未消费`updated_at`。没有外部运行报告时返回UNKNOWN/UNREPORTED，不能由最后同步时间推导RUNNING/FINISHED |
| 行与范围元数据 | 现有树/ledger/detail/表图/关系，补原条号投影/编号角色/依据；直属与子树计数、派生与分析单元数、覆盖状态 | Matrix中的2.1/2.6/2.10/V-01已存在，贯通到reader/outline；结构与台账不能各推原号 |
| 动作能力 | 每项`action_id, supported, enabled, reason_code/reason, target_scope_kinds, execution_target, effect` | 替代`Boolean(sourceReader)`和URL名推权限；能力缺失时不发命令。native也受真实运行、阶段及来源/版本状态约束 |
| 协作记录 | 公开事件/消息、成果提交、确认、反馈与修订回执；每条有稳定ID、来源/任务、时间、所涉版本；增量游标或快照版本 | native复用已有SSE/JSONL；plugin先投影现有保存/确认/反馈记录即可，无需先造SSE流。没有取回回执时保持“待取回/未知” |
| 导出描述 | 当前查看版可导出的种类、范围、状态、精确下载入口/摘要；未决发现和部分成果说明 | plugin已有`export?revision`；native已有草稿和不可变交付历史。默认导出该版全部已保存成果，不默认按当前可见/折叠行截断 |

`reason_code`用于稳定交互，面向工程师显示清楚原因。真实执行目标是能力的一部分：`EXISTING_NATIVE_RUN`、`EXTERNAL_INBOX`、`PROGRAM_EXPORT`或`OPEN_HOST`等效果不能只压成“执行成功”。字段名称可在共用类型对齐时调整，语义不能省掉。

### P2 要接的动作

| 动作 | native适配 | 外部plugin适配 | 成功回执必须区分 |
|---|---|---|---|
| 查看版本/阶段/详情、读取活动 | 复用现有读接口 | 复用session/reader/record/stage | 只读成功，不触发模型或换查看版 |
| 保存范围反馈 | 投到明确当前任务/当前范围；是否送达由真实回执决定 | 投到对应session、版本和对象收件箱 | 已保存、已送达/取回、插件报告修订、用户核对分别记录 |
| 确认指定Map | 复用当前确认及既有任务续接语义 | 复用`confirm-map`，不启动native模型 | 确认已存及后续效果：已安排继续/等待外部取回 |
| 补充当前运行、暂停、继续既有任务 | 仅运行状态与能力允许时可用 | 当前不支持时明确原因；有外部宿主能力后再接 | 发送成功不等于任务已执行完毕 |
| 从空文档发起任务 | 仅明确选择native执行且有实际能力时调用现有启动入口 | 当前提供接入/外部接续说明；没有启动能力就不显示可执行的“开始处理” | 新建任务、仅打开外部宿主、仅复制说明要分开 |
| 导出当前查看版草稿 | 复用同版程序导出 | 复用指定revision导出 | 文件与明确成果依据一致；不是人工接受 |
| 打开外部原任务/复制接续说明 | 作为明确导航能力，若存在 | 提供验证过的宿主链接；否则返回可复制的有上下文说明 | 打开/复制成功，不声称已唤醒模型 |

P2的每个写动作至少提交：`command_id + work/producer引用 + source_sha256 + viewed revision/相关工件摘要 + 对象/范围 + 具体命令`。服务器仍校验实际来源、动作权限和版本前置；不能依赖按钮置灰代替校验。结果返回`command_id、保存回执、实际effect、状态、结果/当前版本引用`；冲突回执应允许UI保留原草稿并展示当前版本。

现有plugin服务端已有幂等基础，但 `PluginWorkbench` 在反馈/确认时每次生成新UUID（62/81行）；迁移到共享命令适配时应保留未决命令ID供断线重试。不要为这项UI接入重做后端幂等存储。

**不用卡住P2的能力：**外部自动唤醒、完整人工响应/内部证据传输、插件FORMAL锁定、页面内逐条历史diff。其能力可以明确返回不支持/未接入，主区和协作区仍完整存在。native已支持的人工意见/正式交付继续保留，只在对应真实成果和就绪条件下出现。

**发现合同的衔接：**编号候选/回源核验由业务任务负责，UI负责统一的发现提示、定位和处置入口。初期无发现服务时返回“尚未检查/能力未接入”，不把空数组显示成“没有编号问题”。建议沿用主稿的finding字段，另外明确`scan_state/checked_scope/complete_or_unknown`。这可随P1/P2交叠接入，不要求完成全部编号检测后才恢复协作区。

**历史反馈的最小兼容边界：**当前plugin写接口只接受当前head。P2至少保留查看版草稿并明确处理409，不静默改绑到新版本；是否允许直接对历史版保存意见，由业务侧补充合同。即使将来允许，反馈来源版本与实际被修订版本仍需分别保存。

## 5. UI实施顺序与验收

沿用主稿P1/P2/P3，不单独创建平行计划。共享前端文件由UI任务在实施时负责；业务任务提供API/工具/合同与固定样例。先对齐消费类型、再分别改自己的文件，避免同时改同一组件。

| 主稿增量 | UI侧先做什么 | 与业务侧的交接及退出条件 |
|---|---|---|
| P1/P2开始 | 明确工作引用、查看版、任务摘要、capabilities和动作回执；给出当前native/plugin/历史映射 | 获得可调用、可验证的两种provider数据；未知/不支持明确表达，不用假任务fixture冒充联调完成 |
| P1读取贯通 | 原编号列、章/直属/分析单元统计、发现状态入口 | 消费共用字段；用现有v3验证8/1/2/9及2.6→2.10展示，不改变原件、条目或编号 |
| P2统一外壳 | 将插件数据适配移入同一DocumentWorkSurface；统一Agent面板与输入；保留83px工具栏及派生独立行 | 切换native/plugin后外壳/协作不消失；任务控制仍到正确执行器，外部没有额外native请求 |
| P2纵向切片 | 同一scope贯通Map→必要确认→Items→反馈→新版→当前版Excel；视图切换与版本锁定一致 | 业务侧提供真实接续/保存回执，UI验证命令目标与前后页面。不为UI改版再运行语义模型评测 |
| P3入口迁移 | 分析/交付目的独立渲染；统一文档列表入口；逐个迁移legacy只读、阅读/诊断和旧深链接 | 旧客户版本与意见可回查；旧页面功能有明确替代位置后才退日常入口，不先删数据/代码 |

建议将以下作为本UI切片的明确验收：

1. **同一外壳**：所有日常文档入口（含插件与历史成果）只有一个文档外壳与协作上下文。插件 `task=export` 真正显示交付内容；分析页不因unsupported变成另一套提取页。
2. **协作与执行分离**：外部无运行报告/已结束/不能唤醒时仍能看目标、成果、意见及接续说明；不会伪造RUNNING，也不会向native启动、暂停或续接接口误发请求。
3. **反馈与确认**：至少检查已存未取回、真实取回、插件提交修订待核对三种状态；新版本到达保留正在核对版本和草稿；确认文案与实际后续效果一致。重复点击/断线重试保持同一命令。
4. **编号与来源**：2.6、2.10、V-01、无独立原编号正文、多编号整体及Snn父来源在树/表/详情/Excel一致；显示跳号提醒不补号、不新增需求。未回源发现与已核实原件跳号明确区分。
5. **计数**：合成第2章直属1、子树8 SRC/8原文需求、2派生、9分析单元可复算；折叠、1:1共行和筛选不会改业务总量；部分范围/未知不表示全章完成。
6. **两视图互通**：切换后保留所选SRC/Snn、原页、筛选、查看版及未发送意见。父条款完整，子项独立响应，表格/图片和跨页内容不被摘要替代。
7. **历史兼容**：v1/v2/v3与既有反馈逐字段保持；legacy Set/候选链接可说明去向；读取错误停留在同一scope并可恢复，不以404回退隐藏问题。
8. **就绪与限制**：Map-only、部分Items、分析跳过、人工能力未接入、失败但有成果都有明确可用动作；正常草稿导出只用程序并绑定查看版。导出范围不随折叠/筛选偷偷改变。
9. **真实界面验收**：当前合成联调可验证接口与交互；另用现有大工作版做只读密度/性能/键盘/窄屏检查，保留本轮原有改进。新语义评测由业务任务按主计划另行执行，程序通过与用户接受分别报告。

本次只完成上述审计与方案交接；没有开始P1/P2实现，也不将现有组件复用称为统一工作流已经完成。
